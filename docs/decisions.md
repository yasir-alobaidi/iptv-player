# Decisions (ADR log)

Format: ID · date · status — decision, context, alternatives, consequences.

## ADR-001 · 2026-09-14 · Accepted — Flutter for desktop and Google TV
**Decision:** One Flutter app: desktop (Linux, Windows) first, Google TV second.
**Context:** Needs a polished UI, keyboard and remote navigation, Linux + Windows now and Android TV later. Video must run in native engines.
**Alternatives rejected:**
- Python + PySide6 + libmpv — excellent desktop fit, but no realistic Google TV path
- Electron / web player — Chromium can't decode AC-3/E-AC-3 (silent channels), MPEG-TS needs JS demuxing, no Cast support in Electron
- Kotlin Multiplatform + Compose — good TV story, weak desktop video embedding
- Separate native apps — duplicate work
**Consequences:** Dart across the codebase; libmpv via media_kit on desktop (fvp fallback); TV engine chosen in TV-0; casting uses our own Dart Cast v2 client and a bundled FFmpeg relay.

## ADR-003 · 2026-09-15 · Done for Linux (Windows deferred) — Desktop playback spike results
**Setup:** HP laptop, Ubuntu 22.04.5, kernel 6.8, GNOME on Wayland for the first Intel runs (X11 runs there use XWayland via `GDK_BACKEND=x11`); after the NVIDIA driver install and reboot the session was "Ubuntu on Xorg", used for the real-Xorg and NVIDIA Xorg runs; the NVIDIA Wayland runs used a later "Ubuntu" (Wayland) login; Intel UHD CometLake-H (iHD 22.3.1), GTX 1650 Ti. Flutter 3.47.4 release build (Impeller, OpenGL ES). media_kit uses the system libmpv 0.34.1 with FFmpeg 4.4.2. Spike: `spike/playback_spike` plays each sample as an endless MPEG-TS stream (`-re -stream_loop -1 -c copy`) over loopback, with the Balanced preset and `hwdec=auto-safe`. Per sample: 5 s warm-up, then a 12 s measuring window (45 s for the codec switch). Results in `spike/playback_spike/results/`; `summarize.py` prints the tables.

**Finding 1: media_kit #1404 reproduces on every unpatched build.** Both pub 1.2.6 and main@c533e44, on both Wayland and X11, log `VideoOutput: EGL display or context is invalid` and then `S/W rendering`. On Flutter ≥ 3.38 no EGL context is current on the platform thread where the plugin looks for one. Decoding stays on the GPU but only in copy-back mode (`vaapi-copy`), and the CPU draws every frame: 1.1–1.6 cores busy at 50 fps, and 140–530 dropped frames per 12 s on HEVC 1080p50 and HEVC 4K. main's Linux render code is identical to 1.2.6; it only removes the drops on H.264 1080p50.

**Finding 2: a ~60-line patch fixes it.** `spike/vendor/media_kit_video_egl_display.patch` (applied by `run_matrix.sh patched`): when no EGL context is current, get the EGLDisplay from GDK (`eglGetPlatformDisplayEXT` with the Wayland or X11 native display) and choose an ES2 RGBA8 config. The log confirms the raster thread and mpv use the same EGLDisplay, so the EGLImage handoff works: H/W rendering with zero-copy `vaapi` (`hwdec-interop` `vaapi-egl`). This is the fix proposed in #1404; nothing is merged upstream yet.

**Visual check:** frames grabbed from the patched X11 window (`grab_frame.sh`; GNOME doesn't allow screenshots of native Wayland windows from scripts) show real moving video for h264_1080p50_aac and hevc_2160p25_eac3, not a black or frozen texture.

**Finding 3: zero-copy fails under XWayland.** With the patch and `GDK_BACKEND=x11`, rendering stays on the GPU (same EGLDisplay on both threads), but mpv's `vaapi-egl` interop can't open a VA display from the X11 connection (`libva: vaGetDriverNameByIndex() failed`). Confirmed cause: Ubuntu 22.04's libva-x11 (2.14.0) only has DRI2 code, and XWayland offers only DRI3. It falls back to `vaapi-copy`, which brings back the drops (321 on H.264 1080p50, 511 on HEVC 1080p50, 116 on HEVC 4K per 12 s). The whole patched X11 run was worse than native Wayland:
- VOD first frames took 5.3–5.8 s (Wayland 0.6 s)
- 14 audio underruns and 4 A/V desync warnings
- zap p50/p95 425/3261 ms with plain `-re` (349/382 ms with a burst); the first 3 zaps took 3.1–3.5 s
- the codec switch restarts mpv's video output, which resets `frame-drop-count`; the watchdog must not treat a lower count as an error

Only XWayland is affected: a real Xorg session gets zero-copy (Finding 4), and GTK picks native Wayland inside a Wayland session. Possible fix if we ever need it: on X11, have the patch give mpv a DRM render node instead of the X11 display. (These XWayland results are kept as `results/patched_intel_xwayland.*`.)

**libmpv 0.34.1 names:** all 14 option names in docs/03 exist in libmpv's `options` list, and all accept the Balanced preset values (read back: `cache-secs` 8, `demuxer-max-bytes` 67108864, `demuxer-lavf-probesize` 1000000, `demuxer-lavf-analyzeduration` 1, `stream-lavf-o` as set, and so on). Differences from docs/03:
- `deinterlace` is only a yes/no flag in 0.34.1 (no `auto`). The app implements Auto by reading `video-frame-info/interlaced`, which reports `yes` for 1080i50 and 576i25.

- media_kit sets `subs-fallback`, which 0.34.1 doesn't have; it logs one harmless error.
- Every open logs `Failed to create file cache`. Phase 3 sets `cache-on-disk=no` explicitly, or a `demuxer-cache-dir`.

## ADR-004 · 2026-09-15 · Done (one device) — Casting spike results, device model(s), verified LOAD fields
**Setup:** "Living Room TV", a Chromecast with Google TV (4K) (model from the user; mDNS only says `md=Chromecast`) on a Samsung 4K TV: Android 14 build UTTC.250917.004, cast build 3.72.446070, receiver user agent `Chrome/92.0.4515.0 … CrKey/1.56.500000 DeviceType/AndroidTV`. The laptop is on 5 GHz Wi-Fi (540 Mbit/s, 192.168.1.254/24), the device at 192.168.1.155. The user's second Google TV doesn't answer on the network; they chose to test one device. `spike/cast_spike` is a Dart CLI: multicast_dns discovery, our own Cast v2 client (protobuf `CastMessage`, TLS to port 8009), a shelf relay server on the LAN address (port 38400), and the docs/04 FFmpeg relay (bundled 8.1.2) reading a loopback provider that plays each sample as an endless real-time MPEG-TS stream (`-re -stream_loop -1`). Results in `spike/cast_spike/results/` (gitignored). The user watched the TV and reported picture and sound for the key runs. Testing stopped at the user's request; any further TV test needs their OK first.

**Finding 1: discovery works next to avahi-daemon.** multicast_dns found both Cast devices on the LAN in 5.0 s (the TV and a Nest Mini speaker) with avahi-daemon running, so the two coexist (ADR-006). `md` is just `Chromecast` on this 4K Google TV model, the same string older 1080p Chromecasts use, so docs/04 can't seed HEVC or 4K support from the model name. The `ca` bitmask does separate video devices: bit 0 (video out) is set on the TV (465413) and not on the Nest Mini (198660).

**Finding 2: the Cast v2 sequence works, with two surprises.** CONNECT → GET_STATUS → LAUNCH CC1AD845 → CONNECT transportId → LOAD works against the device's self-signed TLS 1.3 certificate. LAUNCH takes 3.0–5.6 s when the receiver app isn't running (53 ms when it is). The device also sends `LAUNCH_STATUS` (its `status` is a string, `USER_ALLOWED`) and `MULTIZONE_STATUS` on another namespace, and keeps sending after our CLOSE; the spike crashed on each until its parsing was tolerant. After LOAD_FAILED the media session is gone: STOP returns `INVALID_REQUEST` / `INVALID_MEDIA_SESSION_ID`.

**Finding 3: relay-copy results on the device.** Cells: relay output · LOAD → PLAYING · result, with what the user saw and heard where they watched.

| Sample | Relay | Result |
|---|---|---|
| h264_1080p50_aac | TS · 3.3–4.0 s | **plays**: smooth moving pattern, steady tone (4 min, 200 MB) |
| h264_1080p25_ac3 | TS, AC-3 5.1 → AAC stereo · 2.2 s | **plays**: bars and tone steady |
| h264_1080p25_ac3 | fMP4 · 2.0 s | **plays** (not watched; receiver reports 1920×1080) |
| hevc_1080p50_aac | fMP4, `-tag:v hvc1` · 1.8–2.3 s | **plays**: bars and tone steady (2 min); also plays with `hlsSegmentFormat` `"FMP4"`, `"bogus"`, or no field (not watched) |
| hevc_2160p25_eac3 | fMP4 · 3.9 s | before the TV fix: LOAD_FAILED about 1 s after the first segment (also with `"FMP4"`, no field, or `hev1`); after: **plays** at 3840×2160 but **stutters**, tone steady (Finding 7) |
| h264_2160p25_aac (extra 30 s sample) | TS · 4.0–4.9 s | before the TV fix: LOAD_FAILED the same way; after: **plays** at 3840×2160, smooth except a few-second freeze at the sample's loop point, tone steady (Finding 8) |

The relay lists its first 2 segments 3.6–4.9 s after it starts. Receiver requests carry `Origin: https://www.gstatic.com`, so the CORS headers are needed (not tested without them).

**Finding 4: 4K needs the TV's full-bandwidth HDMI mode.** With Samsung's Input Signal Plus off for the Chromecast's HDMI port, the Chromecast never offered 4K and refused every 4K stream, H.264 and HEVC, with a bare LOAD_FAILED about 1 s after the first segment, while 1080p played. After the user turned it on, both 4K samples play. The app can't see the HDMI mode, so it must learn a device's maximum resolution from this failure (docs/04 learning), fall back to a 1080p transcode, and tell the user that a TV setting may unlock 4K.

**Finding 5: BUFFERING in MEDIA_STATUS isn't a stall.** In the live run the user watched (h264_1080p25_ac3), the receiver reported BUFFERING 31 % of the time and flipped state 12 times a minute, yet bars and tone never stalled and `currentTime` kept pace with the clock; an unwatched run showed 46 % and 22 a minute. It was worst when LOAD went out with 2–3 segments listed and nearly gone (5 %) with about 4 (one run each). The app must not treat BUFFERING as a stall; the relay's segment age and IDLE/ERROR are the signals.

**Finding 6: a plain MP4 with Range (BUFFERED) plays and seeks.** `vod_h264_aac_10min.mp4` served from `/f/<token>/media.mp4`: PLAYING 1.1 s after LOAD. The TV opened `Range: bytes=0-`, then a new request from byte 98,304,000 for SEEK 300 s and from 19,464,192 for SEEK 60 s. Each SEEK was answered in 150–185 ms with PLAYING at the target; PAUSE and PLAY worked; the user saw both jumps and the pause.

**Finding 7: open-GOP HEVC breaks FFmpeg's HLS fMP4 segments.** The 4K HEVC stutter most likely comes from the relay output, not the network or the device: the laptop's link was 540 Mbit/s, the tone never dropped, and playback time kept pace. Joining the relay's fMP4 segments shows a duplicated frame time and a two-frame gap at every segment cut. Checked on the laptop with the same relay command each time:

| Source | Relay output | Frame timing |
|---|---|---|
| x265 clip, open GOP (CRA keyframes with leading RASL frames) | HLS fMP4 | 3 duplicates and 3 gaps in 4 segments |
| the same clip, closed GOP (IDR keyframes only) | HLS fMP4 | clean |
| hevc_2160p25_eac3, hevc_1080p50_aac (both open GOP) | HLS fMP4 | the same kind of fault |
| hevc_2160p25_eac3 | HLS TS | clean |
| hevc_2160p25_eac3 | one continuous fragmented MP4 (docs/04 low-latency mode) | clean |
| h264_1080p50_aac (with B-frames) | HLS fMP4 | clean |

x265 defaults to open GOP and real HEVC channels may use it too, so docs/04's "HEVC → HLS with fMP4 segments" can't be the only HEVC path. **Confirmed on the TV in step 6**, with the clean-looping source from Finding 8: HLS fMP4 segments still stutter (user), while the same source as one continuous fragmented MP4 response (`/p/<token>/stream.mp4`, `video/mp4`, `LIVE`) plays smoothly (user): PLAYING 3.3 s after LOAD, one HTTP request for the whole 90 s, 3840×2160. MEDIA_STATUS looked alike for both (BUFFERING 2–4 % of the time), so only watching told them apart. The app sends HEVC as one continuous fragmented MP4 (docs/04). The Cast docs say HEVC isn't supported in TS (not tested).

**Finding 8: the spike's looping test source breaks at each loop.** `-stream_loop -1` on a TS sample with B-frames corrupts video timestamps where the file wraps: on the 30 s H.264 4K sample, a 0.76 s jump, 16 lost frames, and 2 decode errors per wrap, while audio stays continuous. The TV's segment requests stalled for 3–4 s at the wraps (around 30 s and 60 s into the run), matching the freeze the user saw. The relay copies the fault unchanged, so it's a test-source problem. Looping an MKV remux instead removes almost all of it (laptop: all 1500 packets, one gap under 0.1 s, and 4 instead of 102 decode errors per wrap on HEVC 4K), and in step 6 the same H.264 4K cast ran 110 s on the TV with no freeze (user). The spike and docs/06 now loop MKV remuxes.

**Finding 9: a continuous stream's end is final.** Step 6 killed the relay FFmpeg 25 s into a continuous fMP4 cast. The HTTP response ended; the TV didn't reconnect, played out about 4 s of buffer, and reported IDLE/FINISHED (the user reported that it kept playing, most likely before the buffer ran out). So on this path a relay restart or provider drop needs a new LOAD from the coordinator, while HLS lets the receiver keep polling a restarted relay (docs/04 Supervisor).

**Verified LOAD fields** (Google Cast docs, checked 2026-09-15; device results above): LOAD carries `media`, `autoplay`, `currentTime`; `media` has `contentId` (the URL; an optional `contentUrl` overrides it), `contentType` (`application/x-mpegurl` for HLS and `video/mp4` for files both played), `streamType` `LIVE` / `BUFFERED`, `metadata` (`metadataType` 0, `title`, `subtitle`), and `hlsSegmentFormat` / `hlsVideoSegmentFormat`, documented as "only required for HLS content playback using MPL". SEEK takes `currentTime` and `resumeState` `PLAYBACK_START`. Shaka Player replaced MPL as the Web Receiver's default HLS player in 2026 (release notes: SDK 3.0.0150, April), and this receiver ignores the segment-format fields: HEVC fMP4 plays with `"fmp4"`, `"FMP4"`, `"bogus"`, or no field. The `"fmp4"` vs `"FMP4"` question doesn't matter on current receivers, and the app doesn't send the fields (docs/04).

**Status:** done on one device. Step 6 confirmed Findings 7 and 8 on the TV and added Finding 9. Still open: the second Google TV, and a path for HEVC library files (Phase 8). GO / NO-GO: ADR-007.

## ADR-008 · 2026-09-16 · Accepted — Phase 1 foundation choices
**Decision:** the app is built on the structure, tokens, focus model, data layer, test tooling and CI below. Everything here was decided while building Phase 1 steps 1–8; where a choice contradicts an earlier plan or doc, this ADR wins and the doc has been corrected.

**Identity:** application ID `io.github.yasiralobaidi.iptvplayer`, Dart package `iptv_player`, window title "IPTV Player" (a placeholder — the real name and icon are still open).

### The canvas beats docs/05
docs/05 was written before the design canvas existed. Where they disagree, the canvas is what the app implements and docs/05 has been corrected: the top bar is **64 px** (docs/05 said 56), the nav rail has **no Search item** (search is the top bar field plus Ctrl+K and `/`), the focus ring is a **2 px ring with a 4 px glow at 25 %**, and h2 / bodyStrong are **700**, not 600. Canvas values that docs/05 had no token for became tokens: **radius `control` = 10** for buttons, inputs and rows, and the **17 / 14 / 12 px** text styles (`titleSmall`, `label`/`buttonSmall`, `labelSmall`), plus `button` 15/800.

Two additions the canvas does not draw: the rail's **collapse toggle** (docs/05 asks for one; it sits above Settings, where it disturbs the drawn layout least) and, in the design system, everything docs/05 specifies that the canvas has no artboard for.

### Design system
- **Variable fonts, bundled:** `Manrope[wght]` and `JetBrainsMono[wght]`, registered with `LicenseRegistry`. Variable weights render correctly on Linux, so no static instances are shipped. A variable font takes its weight from `fontVariations`, so `copyWith(fontWeight:)` alone does nothing — the nav rail marks the selected item by colour, not by weight, for that reason.
- **Icons are the canvas's own SVGs**, extracted by `tools/extract_icons.dart` into `assets/icons/` and addressed through the `AppIcons` enum, rendered with **flutter_svg 2.3.0** (added to the ADR-002 package table; `crypto` is a new dev dependency for the extractor's hashes). Each icon is identified by a hash of its markup, so redrawing one fails loudly instead of silently dropping it, and a missing icon is a compile error rather than an empty box.
- **`AppTokens` is a `ThemeExtension`** with accent, density and reduce-motion switchable at runtime. Design tokens only outside `lib/design/` (hard rule 9).
- **The focus ring is stroked outside the control** (`FocusRing` + a `CustomPainter`), not a box shadow: a shadow is a filled rectangle behind the box, so on a transparent ghost button it fills the control instead of outlining it. On accent-filled surfaces the ring inverts to `textPrimary` with a 5 px glow at 35 %, since accent-on-accent is invisible.
- **`ChannelRow` draws the programme's progress on the title line** — a 72 px bar after the ellipsized title, as the canvas does. Riding the row's bottom edge (the step 3b choice) strikes through the title in both densities; the step 7 golden is what showed it.
- `EmptyState` and `ErrorState` scroll rather than overflow a short pane; `SurfaceStateOverride` forces hover/focus/pressed for the gallery and goldens.

### Focus and keyboard (also the Google TV foundation)
- **`FocusPane` is a `FocusTraversalGroup`, not a `FocusScope`.** A scope remembers its focused child for free, but it traps Tab — focus could never leave the nav rail. The memory is explicit instead (`FocusPaneController`, with `focusLast`/`focusFirst`/`focusPane`/`items`/`hasFocus`), and both behaviours are tested.
- The shell has **three panes** — rail, top bar, screen. Left/Right between them go through `FocusPaneController.focusPane()` (the remembered item, else the pane's first). The rail binds Right and the screen pane binds Left; a screen with its own horizontal movement binds Left first and wins, because `Shortcuts` resolves from the focused node outwards.
- **Global shortcuts wrap the router's navigator, not the shell**, so they also fire over the search overlay. `/` is an `Action` that disables itself while a text field has focus, which makes `Shortcuts` pass the key through instead of eating it. **Search is a non-opaque route, not a dialog**, so Ctrl+K, Esc and Back agree with each other.
- **A destination shortcut takes focus with it; Enter on a rail item does not.** Ctrl+1 … Ctrl+7 and Ctrl+, mean "take me there", so focus lands on the first control of the screen that opens; Enter or Space on a rail item means "I am browsing the rail", so the item keeps focus and ↑ ↓ keep working. Switching a branch pulls focus into the new route's own scope, so both cases place focus deliberately, in a post-frame callback — the new branch is only traversable once laid out, which costs one frame (~16 ms) before the ring appears.
- **Esc means "leave what you stepped into"**, in order: close what is open → return focus from the chrome to where the user was in the screen → with focus already in the screen, do nothing. It never navigates to another destination. The shell's `CloseTopIntent` action shadows the global one while focus is inside the shell, so it pops as well: `Actions` resolves outwards from the focused node and does **not** fall through to an outer action when the nearest one is disabled.
- **Never write a conditional sibling next to a focusable subtree in a `Stack`.** The rail's active indicator was `if (selected) Positioned(…)`, so every selection change altered the child count, moved the item's subtree by one index, rebuilt its element and destroyed the `FocusNode` holding the keyboard focus. Indicators stay in the tree and go transparent instead.

### Core
- **Our own log rotation** (`RotatingFileOutput`, 5 × 5 MB, exact): logger's `AdvancedFileOutput` only checks size once a minute.
- **No `runZonedGuarded`** — Flutter warns when it wraps `runApp`, and `FlutterError.onError` plus `PlatformDispatcher.onError` cover the same errors. This supersedes the step 2 plan.
- `Result<T>` and `AppFailure` are sealed; details are redacted when a failure is created. `redact()` covers Xtream stream paths, credential query parameters, URL user-info, auth headers, JSON and printed-map credential fields, and exact secrets from a `SecretRegistry`, URL-encoded forms included.
- `meta` is a direct dependency (`@immutable`). Dart 3.13's `unnecessary_type_name_in_constructor` means the unnamed constructor is written `new(...)` / `const new(...)`; a **named generative const constructor cannot be written that way at all**, so those become `static const` fields.

### Data
- **`DateTime` columns are ISO-8601 UTC text** (`store_date_time_values_as_text: true`). drift's other option is unix seconds, which it reads back as *local* time, so `DateTime.utc(...)` does not survive the round trip — a DAO test caught it. EPG times stay integer epoch ms in their own columns (docs/02).
- The `settings` table holds **one JSON document per key**, and readers fall back instead of throwing, so one corrupt row cannot stop the app from starting.
- **`sources` has no password column** — only `credential_ref`, the flutter_secure_storage key — and a test asserts it.
- The database is opened through a `LazyDatabase` over `NativeDatabase.createInBackground`, so neither opening the file nor any query touches the UI isolate. `bootstrap()` falls back to an in-memory database with a logged error rather than refusing to start.
- **Narrow interfaces keep drift out of the UI** (hard rule 6): `WindowBoundsStore` and `UiPreferences` live in `lib/core/`, their settings-table implementations in `lib/data/`. `railExpanded` is a plain getter read once in `bootstrap()`, so the first frame draws the remembered rail instead of flipping a frame later.
- `build.yaml` needs its `databases:` entry before `drift_dev make-migrations` will run at all. `sqlite3_flutter_libs` stays dropped: an FTS5 smoke test proves the `sqlite3` package's binaries are enough, which ADR-002 had only assumed.

### Window
Size and position are saved debounced and restored on the next launch, through the settings table. Minimum window 1024 × 640. **Two things are still unverified on this machine:** window_manager #585 (a crash when the window is closed) and whether the compositor honours a restored position on Wayland — neither can be tested from a script here, because closing a window and taking a screenshot both fail on this Wayland session.

### Testing
- **Goldens are recorded on Linux only** — text rasterizes differently on Windows, so the same widget is a different image. The mechanism is `@Tags(['golden'])` at library level (`group()` takes no `tags` parameter), the tag declared in a root `dart_test.yaml`, and `skip:` with a reason off-Linux; Windows CI runs `flutter test --exclude-tags golden`. Images live in `test/golden/images/`. A green golden only means nothing changed — read the PNG after re-recording.
- `test/flutter_test_config.dart` loads the bundled variable fonts with `FontLoader` for every test under `test/`, from disk rather than `rootBundle`, so no asset manifest is needed. The debug banner is suppressed for goldens with Flutter's own `debugAllowBannerOverride`, leaving `lib/` alone.
- **`tools/fake_provider` is its own package** with its own `pubspec.yaml` and an `analysis_options.yaml` that includes very_good_analysis, so it carries the app's lints. The root `flutter analyze` **does** reach into it, which is why CI must `pub get` it first. Its data is deterministic and lazily generated from **index-addressable** draws (splitmix64 over seed, a per-kind salt and the index), not a sequential `Random(seed)`: item N must not depend on N−1 having been built. Value quirks are baked in by the generator, representation quirks applied at serialization by `JsonShape`, so one generated row can be served either way. Streams loop an **MKV remux**, never the `.ts`, and every ffmpeg process has a PID file, a kill on disconnect and a startup sweep that only signals a pid whose `/proc/<pid>/cmdline` still matches (hard rule 8).
- `integration_test/app_launch_test.dart` pumps the real `IptvPlayerApp` with `bootstrap()`'s non-disk overrides. `bootstrap()` itself takes no overrides and resolves `AppPaths` on its own, so driving it from a test would write a log and a database into the user's real app-support directory and take over `FlutterError.onError`; a deeper launch test needs an injectable seam first.

### CI
One matrix job over **ubuntu-22.04** and windows-latest, with Flutter pinned to **3.47.4** (the version the goldens were recorded on). 22.04 rather than `ubuntu-latest`: it matches the development laptop and the AppImage target (libmpv 0.34.1), and 24.04 would silently change the mpv the app is tested against (ADR-003). `git config --global core.autocrlf false` runs **before** checkout, or Windows checks out CRLF and `git diff --exit-code` after `build_runner` reports every generated file as modified. CI installs no VA-API driver, no avahi and no protoc — it builds and tests, it never plays or casts — and the fake provider's ffmpeg tests skip themselves because neither the binaries nor the generated samples are committed.

**Alternatives rejected:**
- Following docs/05 where the canvas disagrees: the canvas is the drawn design and the thing the user approved; docs/05 was written first and has been corrected instead.
- `FocusScope` for panes (traps Tab), a box-shadow focus ring (fills transparent controls), unix-seconds `DateTime` columns (loses UTC), a sequential `Random(seed)` in the generator (breaks lazy per-id generation), one component sheet golden (one 1280 × 800 viewport would only ever show the buttons), and two separate CI jobs (each step would be written twice).
- Leaving focus where it was on a destination shortcut: it costs a keyboard user a Tab walk back into the content every single time.

**Consequences:** Phase 1 is complete in code — 259 app tests, 81 fake-provider tests, analyze and the format check clean, release bundles building on Linux. **Still open:** CI green on both OSes (needs a push; the Windows job has never run anywhere), the window_manager #585 check, Windows playback (ADR-007), and the app's real name and icon. The rules above are the ones later phases must not relitigate without new evidence; docs/05, docs/01 and docs/06 have been corrected to match.

**2026-09-18:** CI green on both OSes on its first run (run 35312720884, commit 2e1affd) — the Windows job built and tested the project for the first time, including `flutter build windows --release`. That closes the CI item; the window_manager #585 check, Windows playback and the name and icon remain open.

## ADR-009 · 2026-09-18 · Accepted 2026-09-19 at the phase exit (CI to confirm on the push) — Phase 2 sources, sync and data choices
**Decision:** the Phase 2 choices below. Like ADR-008, it is organized by theme and wins over any earlier doc; docs are corrected as each step lands. It moves to Accepted at the phase exit.

**Plan approved 2026-09-18** (docs/plans/phase-2-providers-and-data.md), with the recommendation taken on all four questions: you run onboarding against your real provider at the end of step 6; `favorites` and `watch_history` wait for the phases that write them; M3U file and URL ship together; sync *duration* is asserted in CI, and frame times are measured by a separate manual benchmark rather than gated.

### Schema v2 (step 1)
- **Tables:** `sync_runs`, `categories`, `channels`, `movies`, `movie_details`, `series`, `episodes`, plus the external-content FTS5 tables `channels_fts`, `movies_fts`, `series_fts` (docs/02 lists the columns). Every child table cascades from `sources`, so removing a source removes its whole catalogue; a swept category sets its items' `category_id` to null ("Uncategorized") rather than deleting them.
- **Mark-and-sweep uses a run id, not a timestamp.** `sync_runs.id` is the marker: each upsert writes `seen_run = <run id>`, and only a succeeded run sweeps `seen_run IS NULL OR seen_run != <run id>` in its own source. The same table records each run's outcome, failure kind and counts for Settings → Sources, and a run still `running` on launch is failed as `interrupted`.
- **Categories are unique per `(source_id, kind, remote_key)`**, not `(source_id, remote_key)`: Xtream numbers live, VOD and series categories independently, so `category_id = 1` exists once per kind.
- **The user's category order and the provider's are separate columns.** `position` is rewritten by every sync; `sort_order` is null until the user reorders, and display order is `sort_order IS NULL, sort_order, position` — a category that appears later lands at the end instead of shuffling the user's list.
- **Upserts rewrite only provider-owned columns** (`INSERT … ON CONFLICT DO UPDATE SET col = excluded.col` for an explicit list), so renames, hidden flags, user order, movie details and fetched episodes survive a re-sync, and row ids are stable. drift cannot infer the types of `DoUpdate.withExcluded` through `Batch.insertAll`; the type arguments are written out.
- **M3U items carry `stream_url` (credentials replaced by placeholders) and `extras_json`**; Xtream items leave both null because their URLs are built from the source. `movie_details.cast` is `cast_names` because `CAST` is SQL.
- **FTS is maintained by triggers**, with `WHEN old.name IS NOT new.name …` on the update triggers. Measured on 50k channels in 5,000-row batches (in-memory, this laptop): a first insert takes 2.0 s with triggers against 1.0 s without; a re-sync with unchanged names costs **nothing extra** (0.97 s both ways); dropping the triggers and running FTS5 `rebuild` afterwards costs 0.1 s. Triggers cost ~1 s per 50k new or renamed rows and cannot be forgotten by any writer, so they stay; step 5 revisits only if the 60 s budget is tight. Tokenizer `unicode61 remove_diacritics 2` with `prefix='2 3'` for type-ahead; changing either is a drop-and-rebuild, not a data migration.
- **Triggers are recreated after every upgrade, not inside a step.** drift's step-by-step `SchemaN` classes do not include triggers, and **its schema verifier does not compare them** — with the trigger step removed, every verifier test still passed and only the search test on a migrated database failed. That test is the guard. FTS consistency in tests uses FTS5's own `integrity-check`, which was confirmed to throw on a stale index.
- **The migration tests moved to drift's own layout**, `test/drift/app/` (`migration_test.dart` and `generated/`), because `make-migrations` regenerates there on every run; Phase 1's hand-made copy in `test/data/db/generated/` would have silently gone stale. The tests: every version to every later one, the live schema against the latest dump, a populated v1 database keeping every source and setting, and a migrated source taking a catalogue that search finds.

### Credentials and sources (step 2)
- **`CredentialStore`** (`lib/core/secure/`) is read/write/delete/keys over opaque strings, returning `Result`; `SecureCredentialStore` (`lib/data/secure/`) wraps flutter_secure_storage, and `InMemoryCredentialStore` (with a `locked` switch that fails like a locked keyring) is what tests and CI use. **A new `SecureStorageFailure`** gets its own message — "unlock your keyring, or check one is installed" — rather than `StorageFailure`'s "check disk space", which would send the user to the wrong place. The failure's detail is the plugin's code and message only, never a `PlatformException`'s `details`, which can echo the arguments back (tested).
- **No plain-file fallback when the keyring is missing or locked.** docs/01 had listed "encrypted file" as the fallback; it contradicts hard rule 3 and is gone. Saving a source fails with the keyring message instead.
- On Windows, flutter_secure_storage 11 keeps values in an **encrypted file whose AES key lives in Credential Manager**, not in Credential Manager itself (docs/01 corrected). Linux keeps one libsecret item per app.
- **One JSON secret per source** under `credential_ref = source.<id>`: the Xtream password, the real playlist URL, the real EPG override URL. M3U files with no EPG override have no secret and a null `credential_ref`.
- **Playlist and EPG URLs are stored as their origin only (`http://host/…`), not masked.** The first version stored `redact(url)`; the hard-rule test caught a playlist URL with a token in its path (`/p/tok…/list.m3u`) going through `redact()` unchanged and into the database file. No pattern can recognize every panel's token, so the database keeps only what is certainly safe.
- **The Xtream server URL is normalized** on save: `http://` assumed, user-info, query, fragment and trailing slashes dropped, a base path kept (`https://panel.test/iptv`).
- **`SourceCredentials` is hand-written, not freezed:** a generated `toString()` would print the password; this one prints the masked URL and `password: ***`.
- **Write order:** add writes the secret first and removes it again if the row insert fails; update restores the old secret if the row update fails; remove deletes the row first (the source is gone for the user, catalogue included) and a secret the keyring won't delete is logged and **pruned later by `pruneOrphanedSecrets()`**. That runs right after the keyring was used successfully — the sync engine calls it once a session — **never on its own at launch**, because listing a locked keyring prompts for the password, and an app that prompts on every start with nothing to sync is broken.
- **Secrets stay in the `SecretRegistry` after a source is removed:** another source may share the value, and over-masking a log is harmless.
- **Blank password on edit keeps the stored one**, so an edit form never needs to show it. A source can't change its type.
- **`SourceType` and `LiveFormat` moved to `lib/features/sources/domain/source.dart`** (the domain can't import drift); `tables.dart` re-exports them and the stored text values are unchanged. `SourceRepository` and `Source` live in `lib/features/sources/domain`, `DbSourceRepository` and the providers in `lib/features/sources/data`.
- Ids are 128 random bits as hex: unique without coordination and meaningless in a log.
- **For step 3:** Xtream's account payload repeats `user_info.username` and `user_info.password`. They must be stripped before anything is written to `account_json`.
- **Verified by hand on this machine (2026-09-18):** GNOME Keyring, login collection unlocked — a throwaway integration test through the real plugin wrote, read back (non-ASCII included), listed, deleted and confirmed the absence of a test key, leaving nothing behind.

### The Xtream client (step 3)
- **`XtreamClient`** (`lib/data/providers/xtream/`) takes the server, username, password and User-Agent as plain values — the caller gets them from `SourceRepository.credentialsFor()` — and returns a `Result` from every call: `account`, the three category lists, `liveStreams`/`movies`/`series` (optionally by category), `movieInfo`, `seriesInfo`, `shortEpg`. `cancelAll()` cancels the request in flight and the queue behind it.
- **Tolerant parsing is hand-written readers, not json_serializable converters** (`tolerant_json.dart`, `provider_text.dart`, `xtream_parse.dart`). A generated `fromJson` fails the whole row on one wrong type; the readers turn a bad value into null, so only a row with no usable id is dropped (and counted in `skipped`). The models are freezed for equality only. Text cleanup (entities, U+FFFD from malformed UTF-8, whitespace) and image-URL cleanup are shared with the M3U parser.
- **The default User-Agent is `VLC/3.0.20 LibVLC/3.0.20`** — the agent panels expect; a source can override it.
- **Request discipline:** one request at a time per client (a future chain), in the order asked; every URL rebuilt from the source's server, so a redirect's token is used once and never remembered; 429/5xx retried with backoff or `Retry-After` (capped at 30 s), three attempts in all; a refused connection and the onboarding check are never retried.
- **dio's `receiveTimeout` is not used.** It cancels and recreates a `Timer` for every received chunk; on the fake panel's 50k-channel list (one chunk per row) that blocked the UI isolate for ~1 s, found by bisecting dio's options. The body is read as a stream with our own idle watchdog — one periodic timer per request, 30 s without a byte — which also turns a stalled body into a retry. **Measured on the `large` profile with the server in its own process:** 50k channels 0.7 s end to end (was 1.3–2.6 s), 30k movies 0.57 s, 3k series 0.09 s, worst main-isolate gap 16–32 ms once warm (was ~1 s; the first call pays JIT compilation, which a release build doesn't).
- **Bodies over 256 KB are decoded and parsed in a background isolate**, through a static helper so the closure sent to the isolate can never capture the client (its Dio can't cross). Results come back through `Isolate.exit`, uncopied. In step 5 the whole sync runs in its own isolate, so on the UI isolate only small calls (the account, details pages) ever run.
- **The fake provider is a path dev-dependency** so tests start it in-process on a free port. Two traps, both in docs/06: flutter_test's fake `HttpClient` answers 400 to everything (`HttpOverrides.global = null`), and an in-process server's own JSON encoding shows up as the client's jank, so timing runs use a separate process.
- **Testing a dropped connection needs a raw socket:** `HttpServer`'s `detachSocket()` leaves the connection open and the client just waits. Through dio a real drop arrives as an `HttpException` whose message quotes the full URL, password included; `AppFailure` redacts it (tested).
- **Invisible characters are written as escapes** (`'\ufeff'`, `'\ufffd'`, `\u00a0`), never literally; the file-writing tool turned escapes into the characters twice, and a check for them ran clean before commit.

### M3U and get.php (step 4)
- **A streaming parser with a callback, not a list.** `parseM3u(bytes, onEntry)` holds only the current line; `readM3u(input, onEntry)` opens a file or URL in the calling isolate, and `readM3uInBackground` wraps it in a new isolate that sends entries back in batches of 5,000. The sync engine (step 5) runs `readM3u` inside its own isolate, so entries are never copied between isolates on that path. Inputs are plain values (`M3uFileInput`, `M3uUrlInput`) so an input, not its bytes, crosses into the isolate. **Measured:** 50 MB / 221k entries in 3.8 s, worst UI-isolate gap 17 ms, peak RSS 238 MB.
- **gzip is detected by its magic number**, not a file name or a header, because servers send `.m3u.gz` as `application/octet-stream`; `Content-Encoding: gzip` is left to `HttpClient`.
- **Attributes are read by a hand-written scanner**, not a regex: the title starts after the first comma outside quotes, an unclosed quote ends at the next comma (so it can't swallow the title), and single quotes and unquoted values are accepted.
- **Credential placeholders in stream URLs** (`{username}`, `{password}`, `{token}`) from the playlist URL's query, matched on whole segments and query values, with a fixed priority where two secrets share a value. `fillUrl` reverses it at play time. **Known limit:** a credential the playlist URL doesn't carry (a per-line CDN token) can't be recognized and is stored as sent; the playlist's own URL is already secret-stored (step 2).
- **Identity = FNV-1a 64-bit** over tvg-id, name and a normalized path (no query; an Xtream path's two credential segments dropped), 16 hex digits built from two 32-bit halves — `toUnsigned(64)` can't make a VM int positive, and the first version printed negative hex for half of all identities. Two values are pinned in tests and matched an independent Python implementation.
- **Classification adds a video-extension rule** to docs/02's path rule (`.mp4`, `.mkv`, … → movie) for plain VOD lists without `/movie/`.
- **`IdleTimeout`** (`lib/core/streams/idle_timeout.dart`) is the shared form of step 3's watchdog: one periodic timer per stream, pauses excluded. The Xtream client and the M3U reader both use it; `Stream.timeout` is avoided for the same per-event-timer reason as dio's `receiveTimeout`. `defaultUserAgent` moved to `lib/data/providers/provider_http.dart`.
- **The fake provider's `get.php`** streams the catalogue as an Xtream export (live, movies, every episode as `Series S01 E02`), 401 on wrong credentials, `type=m3u` for titles only, `output=m3u8`; a new `messyM3u` quirk (on in `quirky`) adds CRLF, `#EXTVLCOPT` and `#KODIPROP`. `player_api.dart`'s wire encoder and request origin are now public for it.
- **A `benchmark` test tag, skipped unless asked for** (`flutter test --tags benchmark --run-skipped`): the Phase 2 decision-4 way to keep timing out of CI while keeping the measurement in the repo. The 50 MB playlist itself is generated at test time (too big to commit); CI checks it is read whole and correctly.
- **`.gitattributes` marks `test_fixtures/**` `-text`**, so CRLF, lone CR, BOM and invalid-UTF-8 fixtures stay byte-exact on every checkout.

### The sync engine (step 5)
- **The spike (the phase's one unknown): drift from a background isolate works, but not over Phase 1's opener.** `serializableConnection()` hands another isolate a `DriftIsolate` to connect to, but only when the database's executor exposes the one it runs on. Behind `LazyDatabase(() => NativeDatabase.createInBackground(file))` drift can't see it, and starts a proxy server **on the UI isolate** that relays every statement, one connection per call. Measured, 50k channel upserts from a sync isolate in 5,000-row batches: through the proxy 2.2 s with a worst UI-isolate gap of 23 ms; **direct 2.0 s (re-sync 2.2 s) with a worst gap of 9 ms**, and the UI's query streams saw every batch land. `openAppDatabase` is now async and returns `NativeDatabase.createBackgroundConnection` after creating the directory, so the one step that can throw does so inside bootstrap's `try`. `app_database_open_test.dart` guards it (a direct connection has the same port every time; a proxy is new each call). `computeWithDatabase` wasn't used: it has no progress or cancel. The sync runs in `startBackgroundJob` with the `DriftIsolate` in its message.
- **Killing an isolate in the middle of a transaction blocks the database for everyone** (spiked: the UI connection's next query was still waiting after 10 s). *(Corrected in ADR-011 step 3: a batch is itself a transaction the client opens and commits, so a kill inside one blocks the database the same way. Writing isolates are now stopped with `startGuardedJob`, which never kills inside a transaction.)* Killing one between batches is clean (whole batches only, FTS consistent, the next isolate connects normally, and drift's server drops the dead client by itself). So **the sync isolate never opens a transaction**: every write is one batch, which the database isolate applies whole, and cancel and timeout simply kill the isolate. The run's start (`sync_runs` row) and its finish (sweep, outcome, `last_synced_at`) happen on the UI isolate's connection, the finish in one transaction; a crash there leaves the run `running`, failed as interrupted on the next launch.
- **Where things live:** `SyncService`, `SyncProgress`, `SyncReport`, `SyncStatus` (idle, running, succeeded, failed, cancelled) and `ProviderAccount` in `lib/features/sources/domain`; `SyncEngine`, the isolate body `runSyncWork`, `XtreamSync` and `M3uSync` in `lib/data/sync/`; `syncServiceProvider` and `syncStatusProvider(sourceId)` next to the source providers. Nothing in the isolate logs (the log can't cross); it returns warnings, without URLs, for the engine to log.
- **Credentials are read on the UI isolate** (the keyring plugin answers only there) and travel to the isolate as plain strings in `SyncWork`, whose `toString()` redacts. `pruneOrphanedSecrets()` runs once a session, right after the first successful keyring read.
- **Progress follows the `OnboardingSync` artboard**: the stage, a count per list, the current list's total once it has arrived ("8,021 of about 13,800"), and the account after the account stage. There is no "current item": the artboard shows none.
- **Xtream:** the account first, saved at once (so an expired account shows even if a later stage fails), then all three category lists, then live, movies and series, 5,000 rows a batch; any failed request fails the run, and nothing is swept. **A missing or dangling category is a null `category_id`**, not a synthetic "Uncategorized" row: the schema already has the null and the counts query already groups by it.
- **An Xtream list that comes back empty keeps the last one**, and its categories with the user's hidden flags: an empty `get_vod_streams` is far more often a panel's hiccup than a provider that dropped every movie. It is logged. **Two empty runs in a row are taken at their word** (added after review): the run records the kinds that came back empty in its `counts_json` (`"empty": ["movie"]`), and when the previous *successful* run recorded the same kind, this run sweeps that kind's items and categories. A glitch costs one refresh of stale data; a real removal lingers one refresh interval, not forever.
- **M3U:** a `group-title` becomes a category of the entry's kind the first time a run meets it; episodes form series by `(group, series name)` — `seriesIdentity`, the same FNV-1a with an `s` prefix, so it never equals an entry identity — so "Dark" in a dubbed and a subtitled group stays two series. **An episode whose name has no numbering joins a series named after its group, numbered in playlist order; with no group either, it is filed as a movie**, a lone video the user can still find. M3U episodes are upserted and swept with the run (`upsertEpisodes`, `sweepEpisodes`, M3U only: Xtream episodes carry no run and would all go). The movie's `ext` comes from its URL, and `extras_json` holds `user_agent`, `referrer`, `catchup`, `catchup_days`, `catchup_source`, `tvg_name` when present. **A playlist with no entries fails the run** rather than emptying the source.
- **The playlist header's EPG URLs go to the keyring** (`SourceRepository.setAdvertisedEpgUrls`), written only when they changed; a playlist file with no EPG override gets its secret document on demand. `SourceCredentials.advertisedEpgUrls` hands them to Phase 4.
- **The M3U parser got backpressure:** `onEntry` may return a future, and the parser pauses its subscription until it completes (not `await for`, which would cost a suspension per line). Memory holds one batch, not the playlist.
- **Launch:** `bootstrap()` now builds a `ProviderContainer` and runs the app under `UncontrolledProviderScope`, so after the first frame plus 2 s it can call `SyncService.startUp()`: runs left `running` are failed as interrupted, then each source older than its `refresh_hours` syncs, one after another. Widget tests are untouched. Onboarding (step 6) and manual refresh (step 7) call `sync()`; a second call for the same source joins the first.
- **Tests:** the engine end to end on a real file database (`sync_engine_test.dart`: the fake provider's `default` and `quirky` profiles, a re-sync against a smaller catalogue that keeps every user choice and removes exactly what went, a proxy that makes one call 404 or come back empty, wrong password, M3U grouping, a changed, missing or empty playlist, cancel, join, launch); **a real crash** (`sync_kill_test.dart`: a `dart run` process SIGKILLed after 5,000 rows, then `PRAGMA integrity_check`, the FTS checks, the old catalogue and a hidden category intact, the run failed as interrupted, and the next sync completing — `dart run` runs the script in the process it starts, checked, so the kill hits the sync itself); and the hard-rule-3 test now syncs a playlist that repeats the password in every path and in its EPG header, and one with a token in its URL path, then scans the database file.
- **Measured (benchmark tag, debug JIT under `flutter test`, this laptop):** the `large` profile, fake provider in its own process — **first sync 6.5 s, re-sync 3.9 s** against the 60 s budget, worst UI-isolate gap 31 ms and 26 ms, database 24 MB, peak RSS 427 MB for the test process. A 27 MB, 200k-entry playlist file: 16.2 s, worst gap 20 ms, peak RSS 234 MB. Both paths cost about 75 µs a row, mostly the upsert and its FTS trigger, so the triggers stay (step 1's question is closed). The 31 ms is under the 32 ms frame budget but close; its cause wasn't investigated, and step 8 measures it again in profile mode.
- **Removing a source goes through `SyncService.removeSource()`** (added after review), never `SourceRepository.remove()` directly: it refuses new syncs for that source, cancels the running one and waits for it to end, then removes the source (its catalogue and runs cascade) and resets its status to idle. A sync asked for meanwhile fails as `NotFoundFailure`. Tested mid-write: nothing of the source is left, and the FTS indexes check clean.
- **The launch refresh may ask to unlock the keyring:** kept. libsecret offers no way to ask whether a collection is locked without prompting, and most desktop sessions unlock the login keyring at sign-in. It happens only when a source is due, never with nothing to sync.

### The watchdog (step 4)
- **In the coordinator**, per docs/03: open timeout from the preset (8 / 12 / 20 s); while playing, a one-second tick: the position must move unless the player is buffering (a stall after 8 s), and buffering may last 15 s; a live stream that ends is a drop. Each of those is a `network` problem and is retried. Backoff 1, 2, 4, 8, 15, 30 s, the URL built again from the source every time and the dead stream stopped first; **a first frame resets the count**; after 6 failed attempts, `PlaybackFailed`. A full account (`connectionLimit`) is tried 3 times, not 6. Zapping or Retry cancels a pending retry by token.
- **Classifying a failure (`HttpStreamProber`, `classifyStreamFailure`):** mpv reports failures as text, so after it lets go, one GET of the stream URL reads the status and at most 512 bytes of an error page, then cancels at once (the slot must be free for the next attempt). 2xx → a moment's failure, retried (`unsupported` if mpv's text names the decoder); 429 → limit; 401 / 403 / an empty 404 on an Xtream source → the account is read too: sign-in refused → `auth`, `active_cons ≥ max_connections` or a "max connections" body → `connectionLimit`, not Active → `auth`, else a 403 is `auth` and an empty 404 `offline`; other 4xx → `offline`; 5xx → `server`, retried; no answer → `network`, retried. Every problem carries an `AppFailure` with the HTTP status, so the failure card can say what the server answered.

### The soak run (2026-09-19)
Run on the real display, three times; it found two things.

- **The fake panel leaked a connection slot, and the first hour died of it** (minute 8 on). A client that *resets* the connection before the response headers go out — a player abandoning an attempt mid-reconnect, and the kernel sends a reset whenever a socket is closed with data still unread — left dart:io holding the shelf body: `_HttpOutgoing` sets `_socketError`, drops every chunk it is handed and never cancels the subscription, so `onCancel` (our reap) never ran. Two leaks filled the 2-connection account, every reconnect was refused as full, and the player sat in reconnect-and-fail for 50 minutes. The app was blameless: it retried, backed off and reported the right reason throughout. **Fix:** the relay hijacks the connection for live `.ts` and writes the answer itself, still chunked, so a departed client shows on the socket's read side; nothing is counted until the socket is in hand; the codec-switch timer tests the body's own `ended` flag, because a body cancelled by a departed client is not closed. Regression test: "a client reset before the answer starts frees its slot". The fake server also stops when its stdin closes (`--exit-with-stdin`, passed by `FakePanel`), so a killed test no longer orphans it and its ffmpegs. **This is a warning for the Phase 5 cast relay**, which serves FFmpeg output over our own shelf server: the same disconnect goes unnoticed there unless the relay owns the socket.
- **The memory rule measured the warm-up.** The second hour was clean on playback (78 reconnects, 0 failures, 9 s longest without a picture, 1 connection held throughout) but reported 101 MB growth. It is not a leak: a control run with one open and no reconnects grew 576→653 MB in five minutes and then held flat, and 50 reopens added ~0.3 MB each after the first minute. The player settles over about 40 minutes (a debug build, three codecs, the video output) and then holds: 10-minute medians 584, 632, 640, 664, 678, 674 MB, with spikes of ~85 MB for a sample or two during a reconnect (peak 760). **Decision (the user's, 2026-09-19):** measure growth from minute 21, not minute 6, and compare medians rather than averages so a spike is not growth; the 50 MB budget is unchanged. That hour scores 35 MB, and the **confirming hour under the new rule passed: `soak 60min video on: 545→739 MB (growth from minute 21: 39 MB), 78 reconnects, 0 failures, longest without a picture 9 s`**, never more than 1 connection held, 10-minute medians 598, 652, 655, 686, 695, 691 MB. An 8-hour soak before release is what settles a slow leak; an hour cannot.
- **A dropped stream ends cleanly here, and a real cut does not.** `drop_after_s` ends the chunked body with its last chunk, which lavf reads as the end of the stream, so the watchdog sees it. A real cut connection (no terminator) is absorbed by mpv's own `reconnect_streamed=1` and the app never learns of it. **To do in Phase 4** (the user's call, 2026-09-19): a `cut` fault that closes the connection mid-body, and a test for what the player does while mpv reconnects underneath it.
- **Phase 3 exit:** the fault suite green (video and `vo=null`) · the zap budget met · the 1-hour soak: run, and it paid for itself (above) · CI: to confirm on the push.


## ADR-011 · 2026-09-19 · Accepted (plan approved 2026-09-19; phase exit 2026-09-27) — Phase 4 EPG and guide choices
**Decision:** the Phase 4 choices below, organized by step, as docs/plans/phase-4-epg-and-guide.md proposed and the user approved on 2026-09-19 — **the recommendation in all seven decisions and both sketches** (Settings → Guide, the programme detail sheet).

The seven, in short: **1** XMLTV is the guide once imported, the panel's short EPG only answers for an unmatched channel or a window that has run out, behind one `CompositeGuide`. **2** the import writes plain batches into staging tables and the **UI isolate** swaps them in one short transaction — never a transaction inside the isolate (the Phase 2 kill spike). **3** schema v5: `epg_channels`, `epg_programs`, `epg_mappings`, two staging tables, `programs_fts` built now and queried in Phase 6. **4** retention now − 1 day to now + 7 days applied while parsing, days a global setting, the time offset per source, and a change re-imports. **5** refresh when older than 24 h, checked at launch and hourly, after a sync and never beside it, one source at a time, plus a manual refresh; the "Guide updated · N channels matched" toast; a failure keeps the old guide. **6** the grid is a vertical list of rows over one shared horizontal offset, not `TwoDimensionalScrollView` (its cells are uniform, ours are time-width). **7** the grid queries the visible window plus a screen and an hour of margin, cached, with fast scrolling cancelling in-flight queries.

Out of this phase: Home's rows and now/next on Home favourites (Phase 5 — Home is still a placeholder), the search overlay (Phase 6 — the index is built here, no UI), catch-up playback (the archive phase).

### The fake provider's guide, and the `cut` fault (step 1)
- **`xmltv.php`** (`tools/fake_provider/lib/xmltv.dart`): the full guide for the generated catalogue, from the same deterministic schedule `get_short_epg` answers from, so a channel's now/next matches whichever way the app asked. Streamed in ~32 KB pieces and never built whole — `?days=` (a day of history always comes with it), `?channels=`, `?gzip=1`, and `--epg-days` / `--epg-gzip` for the defaults. A channel with no `epg_channel_id` (the generator's every 9th) is left out, which is the app's "No guide information" case. **Measured: 200 channels × 7 days = 27.9 MB**, about 140 KB per channel-week and ~17× smaller gzipped, so the 300 MB budget file is roughly 2,150 channels × 7 days.
- **Quirks**, each a flag on the request and all of them on in the `quirky` profile (`FakeQuirks.messyXmltv`): `no_stop` (every 7th programme), `bad_date`, `unknown_tz` (`+2500`), `unknown_encoding` (an encoding that does not exist), `duplicate_channel`, `orphan_channel` (a `<channel>` with programmes that no stream matches) and `unclosed` — the last is a test's choice only, never a profile's, since it truncates the file mid-element.
- **`cut_after_s`**: the live body stops with **no last chunk** and the connection closes. `drop_after_s` ends the chunked body properly, which lavf reads as the end of the stream; a cut is what a panel or a network really does, and mpv's `reconnect_streamed=1` reconnects underneath the app (ADR-010 "The soak run"). What the player should do about it is step 7's suite.
- 15 `xmltv.php` tests and one for the cut; the fake-provider suite is 114 tests.

### Schema v5 and the EPG store (step 2)
- **Seven tables, not five.** Decision 3 named `epg_channels`, `epg_programs`, `epg_mappings`, the two staging tables and `programs_fts`; v5 adds two more, both because the alternative was a second migration for the user to review in step 4 or 5:
  - **`epg_imports`** — an import's run record (started, finished, outcome, `AppFailure.code` + HTTP status, counts, and the `is_live` flag the swap moves). It plays the part `sync_runs` plays for the catalogue, but it is its own table: Settings → Sources watches `sync_runs`, and a guide import must not show up there as the source's last sync. Settings → Guide ("updated 2 hours ago", "the last refresh failed"), the step 7 scheduler and the launch recovery all read it.
  - **`epg_matches`** — what the matcher resolved, one row per matched channel, with the rule that matched it. Derived state, rewritten whole after an import or a sync; the user's `epg_mappings` is a separate table so a bug in that rewrite can never eat it. It exists so the guide grid joins `channels → epg_matches → epg_programs` on indexed columns: 50,000 channels × 7 days cannot afford matching names per row.
- **Programmes keep the XMLTV id, not a row id.** `epg_programs.epg_channel_id` is the id the programme names. A file can carry programmes for a channel it never declares (the `orphan_channel` quirk), and the import must be able to stage a row without resolving a parent. The index is `(source_id, epg_channel_id, start_utc)` — docs/02 wrote `(epg_channel_id, start_utc)`, and the source column leads because every query is per source.
- **Times are integer epoch ms** in their own columns, as docs/02 says: drift's `DateTime` is ISO-8601 text, which neither compares nor packs well over hundreds of thousands of rows.
- **Staged rows carry only their import**, not the source — the import knows the source, and a column saved is a column not written several hundred thousand times. The swap supplies the source as a literal.
- **The swap is `INSERT … SELECT` inside one transaction on the app's side**, not a table rename: several sources share these tables. It deletes the source's live rows, copies the staged ones in, drops the staging, moves `is_live`, and records the import as succeeded — all of it, or none. The import isolate never opens a transaction (hard rule 2, the Phase 2 kill spike). The copy and the FTS triggers it fires are a real cost at 300 MB; **step 7's benchmark measures it**, and if the swap is the bottleneck the fallback is a generation column instead of a copy.
- **A killed import costs staging and nothing else**, which the tests show: the live guide, the live import and the user's mappings are untouched, the staged rows stay until the next launch, and then `recoverInterrupted()` — called from `bootstrap()` beside the sync engine's own `failInterrupted()` — marks the import `failed`/`interrupted` and sweeps every staged row whose import is no longer running.
- **`programs_fts` is external-content over `epg_programs`** (title, sub-title, description), kept by triggers exactly like the catalogue's three. Built now, queried in Phase 6.
- **Triggers are recreated only when the upgrade ends at this build's `schemaVersion`.** `_recreateTriggers` creates *all current* triggers, and v5's include one on `epg_programs`; the schema verifier migrates to intermediate versions, where that table does not exist yet. The app always upgrades all the way, so the guard costs nothing and the verifier stops failing. (A row written into a *versioned* schema is written without triggers, so a migration test must insert anything it will later delete after the migration, or FTS5 reports a malformed image.)
- `EpgRepository` (`lib/features/guide/`) is the seam: the import's lifecycle, now/next for a page of channels, a time window for the grid, the guide's channels for the Match… picker, the user's mappings, and coverage. Coverage reads the live import's `counts_json` rather than aggregating the programme table, so opening Settings → Guide costs two small queries whatever the guide's size.
- 13 DAO tests, 17 repository tests, and the v4 → v5 migration: 857 app tests.

### The XMLTV parser and the import (step 3)
- **The parser is its own byte scanner, not the `xml` package** (`lib/data/providers/xmltv/`). ADR-002 named `xml`'s event API and docs/01 a custom tokenizer as the fallback; the fallback is what was built, because it can do what an XML library can't: markup is ASCII in every encoding a guide is read in, so tags are found in the raw bytes and only the slices the guide keeps are ever decoded — a few attribute values and the text of title, sub-title, desc, category and display-name. A programme whose own times put it outside the window is never decoded at all. A token cut by a chunk boundary is carried into the next chunk (at most 64 KiB); comments, CDATA, PIs and DOCTYPEs are small state machines. The `xml` dependency is dropped from pubspec (it stays in the lock file through flutter_svg).
- **Measured** (`flutter test` JIT): a 300 MB guide from disk — 2,400 channels × 8 days, 921,600 programmes — parses in **4.3 s (69 MB/s), max RSS +23 MB**; a 104 MB guide generated on the fly stays within **+15–18 MB** (the default-run test's bound is 64 MB, where reading the body whole would add over 100). The import's budget is 4 minutes, so the time will go to the batch writes and the swap, which step 7 measures.
- **The rules**, each row counted once under the first it fails, by a code stored in `counts_json` and never renamed. As a programme is read: `no_channel` → `bad_date` / `bad_timezone` → `duplicate_programme` (the same start as its channel's pending programme) → `out_of_order` (it starts before it). When its end is known: `no_stop` → `bad_duration` → `too_long` (over 24 h, the repository's look-back) → outside the window (counted, not a fault) → `no_title`. Channels: `no_id`, `duplicate_channel` (first wins). A stop that is missing or unreadable is filled from the next programme's start, and an overlap is cut at it, so each channel holds one pending programme — memory grows with the channel count, never with the file. Also `malformed` (a runaway tag) and `truncated` (the file ends mid-element or without `</tv>`: what was read is kept).
- **Going back in time is a second schedule, and the first one read wins (`out_of_order`).** The end-to-end tests found it: the fake panel gives ten HD/SD pairs one `epg_channel_id`, each with its own schedule, and both were staged — 960 slots with two programmes on at once, which now/next and the grid would have drawn. Guides joined end to end do the same. The first rule said an out-of-order programme just finalizes the pending one; now it is skipped. A file split by day goes forward and loses nothing; one that really lists a channel backwards loses rows and says so in its counts. Deduplicating in the swap was the alternative: a sort over the whole import inside the swap's transaction, and exact only for identical starts.
- **Times:** 14, 12, 10 or 8 digits; the zone optional (UTC, as the DTD says), `±HHMM`, `±HH:MM`, `±HH`, `Z`/`UTC`/`GMT`. Hours over 14, minutes over 59, or a zone name (whose DST rules can't be known here) is `bad_timezone`. The source's offset is added to both ends before the window is applied.
- **Encodings:** UTF-8 (BOM skipped), Latin-1, Windows-1252 and ISO-8859-15 by the declaration. Anything else — including `utf-16` declared over bytes that are plainly ASCII-compatible — reads as UTF-8 and is flagged `unknownEncoding`; a UTF-16 BOM is refused. Malformed UTF-8 is replaced, never thrown on.
- **Entities are decoded twice:** as XML, then by `cleanText` like every provider text, so a name the panel escaped twice (`&amp;amp;` on the wire) comes out as `&` — the same name the Xtream client shows for that channel, which step 4's name matching depends on. Ids and URLs are decoded once. `cleanXmltvText` skips `cleanText`'s regular expressions when no `&` can start an entity (the same result, checked against `cleanText` on 20,000 random strings); it took the benchmark from 31 to 69 MB/s.
- **What is not XMLTV** — an empty body, JSON, an HTML page, another root — is a `ParseFailure`. An error the body ends with (the network, the 60 s idle timeout, a damaged gzip) fails the import and the old guide stays; a truncated file does not fail.
- **The import has the sync engine's shape.** `EpgImporter` (UI isolate) reads the source and its credentials, resolves where the guide is — the user's EPG URL, else the panel's `xmltv.php`, else the playlist's first `url-tvg`; a value without `http(s)://` is a file — opens the import, and starts `runEpgImportWork` in an isolate that reads, parses and stages batches of 5,000 as plain batches, never a transaction. A full batch's write future pauses the parser, so the isolate holds one batch. On success the swap (`commitImport`); on a failure or a cancel, `abandonImport` and `sweepStaging` at once. A second call for a source joins the first; `cancel` and `dispose` kill the isolate. Nothing calls it outside tests yet: when to import is step 7.
- **An import with nothing to keep fails, and the old guide stays.** No programmes staged — an empty answer, or a guide wholly outside the window — is a `ParseFailure`, not a swap to an empty guide.
- **A source with no guide URL, or a locked keyring, records no import.** They are states of the source for Settings → Guide to show, not failed imports.
- **Progress counts wire bytes.** The reader decodes `Content-Encoding: gzip` itself, so `bytesRead` and `totalBytes` are both what crossed the network and the fraction works; a `.xml.gz` served without the header reaches the parser as gzip and is sniffed.
- **The guide's URL never leaves the isolate.** Inside an isolate `AppFailure` has only `redact()`'s patterns — they catch `password=`, not a token in a path — and dart:io's `HttpException` quotes the whole URI. `hideUrl` / `failureWithoutUrl` replace every printed form of the URL with its origin and mask its query values, user-info and long path segments wherever else they appear; they run in the reader, on the isolate's result and warnings, and again on the app side. Tests: a refused connection, a hang-up mid-body, HTTP 500, a password in the query, a token in the path.
- **Killing a writing isolate could deadlock the whole database — fixed with guarded jobs.** The importer's cancel test hung about once in twelve runs under load, and after it the whole test file. The cause is in drift, and it applies to the Phase 2 sync engine as much as to the import: outside a transaction, `batch()` opens one **from the client side** — begin, the statements, commit, three requests — and drift's database isolate never rolls back a transaction whose client died (closing a client only forgets its channel). So an isolate killed between a batch's begin and its commit left the transaction open, first in the server's queue, and every query the app made afterwards waited for good. The Phase 2 spike had killed isolates *between* batches, never inside one, and the design took a batch to be atomic under a kill; it is atomic in the database, not in the protocol. **The fix:** `startGuardedJob` (lib/core/isolates/background.dart) stops a job by asking it first. `openJobDatabase` (lib/data/db/job_database.dart) wraps the job's connection in a drift `QueryInterceptor` that marks every transaction it begins on the job's `JobCancellation`. Asked to stop, the isolate answers as soon as no transaction is open — at once when it is waiting on the network, or when the batch in flight commits — begins none after that, and is killed then; 30 seconds without an answer is the last resort. No write site changed: the sync and the import only connect through `openJobDatabase` and start with `startGuardedJob`. `test/data/db/job_database_test.dart` cancels a job five times as a 20,000-row batch begins and then queries the database from the app's side; with the old kill it times out on the first round (checked), guarded it passes, and only whole batches ever land. The importer and sync tests under 8-way parallel load, which hung 2 runs in 24 before, ran clean after.
- **Also in this step — CI was red on the step 2 push**, and the Linux half was Phase 3's goldens: they draw clock times in the viewer's zone from an instant (the fakes' 12:00 UTC), so images recorded in America/New_York failed on the UTC runner. `goldenNow()` in the golden harness pins them to a local 8 AM — the same instant here, so no image was re-recorded — and they now pass under `TZ=UTC`, `America/New_York` and `Asia/Tokyo`. The full suite is run with `TZ=UTC` before a commit from now on. The Windows job's 3 failures predate this (the Phase 2 exit run had them) and are not diagnosed: its log needs admin rights on the repository.
- **Tests:** 125 parser unit tests (every chunking — whole, one byte at a time, random — must give the same result), a memory test and a benchmark; 109 fixture tests over 29 files in `test_fixtures/xmltv/`, written from the spec by a separate pass rather than from the parser's output; 12 against the fake panel's own guide with every quirk, gzip and `unclosed`; 19 reader, 15 import-isolate and 27 importer tests end to end against the fake provider, including a cancel mid-import (recorded cancelled, no staged rows left, the old guide untouched); 8 guarded-job tests and the deadlock regression test. **1,174 app tests.**

### Matching, and now/next everywhere (step 4)
Built by three agents from one written spec (the matcher; the job that stores matches; the guide the screens see), as in step 3.
- **The matcher** (`lib/features/guide/domain/epg_matcher.dart`) is pure and runs over a whole source at once: rules in docs/02's order behind the user's mapping — **manual** (always wins, kept even for an id the guide lacks) → **exactId** → **caseInsensitiveId** → **normalizedName**. The name rule compares `normalizeChannelName` keys: HTML entities decoded (to the same key whether or not `cleanText` already ran), case and Latin diacritics folded, leading country/language tags stripped only where a separator marks them (`UK:`, `|EN|`, `[US]`, `AR |`, `EX-YU:` — `TV 5 Monde`, `Al-Jazeera`, `RTL-2` keep their first word), quality and technical tags dropped as whole words (HD, FHD, UHD, 4K, HEVC, H.265, 1080p, backup, …, superscript `ᴴᴰ` too), `&` → `and`, `+1` → `plus1` so a timeshift channel never takes its parent's guide, then punctuation to spaces. It tries the guide's display names first, then its ids without a country suffix (`cnn.us` → `cnn`).
- **Ties go to the channel's own country.** When several guide channels share a name key — a guide carrying one channel's feed for several countries — the one whose id ends in the country tag the channel's name carried wins (`UK: Marlow Drama` → `marlowdrama.uk`, never `.fr`; `gb` and `uk` are one country, `usa` is `us`); with no tag, or no feed for it, the id that sorts first, so a run is deterministic. Without this, a UK channel with no guide id took the French schedule, times and all. On the fake panel with ids removed, every tagged channel lands on its own feed (149 of 149 default, 168 of 168 quirky); with ids, every channel that has one matches `exactId`. 50,000 channels against 5,000 guide channels: ~175 ms (debug JIT). A 144-line corpus of real-shaped names (`test_fixtures/epg_matching/names.tsv`) pins the behaviour, including what does *not* match (`5 USA` vs `5USA`, `Köln` vs `Koeln`).
- **Matches are stored by a guarded job** (`lib/data/sync/epg_match_work.dart`): it pages the source's channels and live guide channels out of the database in 5,000-row pages keyed on the row id, runs the matcher once, and rewrites the source's `epg_matches` as **one batch** — delete, then every insert, only for channels that still exist (a sweep between the read and the write leaves a channel out rather than failing the batch on its foreign key). `EpgMatchService.rematch` runs one job per source; calls during a run coalesce into one follow-up, whose result every one of them gets. It runs after every import's swap (the import answers only once its guide is attached; a match failure is logged and leaves the import in) and after every successful sync (`SyncEngine.onSynced`, not awaited). A manual mapping survives a re-sync and a re-import (tested end to end); channels a re-sync adds are matched by the rematch it starts.
- **The screens ask one `GuideService`, now a `CompositeGuide`** (decision 1): `DbGuide` answers from the imported guide whenever it has a programme on now or next for the channel; otherwise — unmatched, run out, or unreadable — the panel's short EPG does, one request for the channel someone is looking at. `GuideService` gained `warm` (a page in one query; a no-op for the short EPG) and `changes` (fired when `epg_imports` or `epg_matches` change — never on `epg_programs`, which an import writes by the hundred thousand).
- **Every Live TV row now shows its programme**, not only the ones looked up: a page is warmed in one indexed query the first time it is drawn (chunks of 500), pages on screen are re-warmed once a minute and at once on `changes`, and nothing is looked up while Live TV is covered (the shell keeps it built behind other destinations and the player; `TickerMode` says so). Phase 3's "rows show only what was looked up" was a network limit; the imported guide is local.
- **The clock rule:** a cached answer never shows a programme that has ended — when "now" ends and "next" has started, next moves up; when both have ended the answer is unknown, not "none". After a `changes` the last answer stays on screen until the fresh one lands (dropping it would blank every row for a frame). `nowNextProvider` asks again at the moment a programme ends or the next starts, so the preview and the OSD move on by themselves; it watches its own `GuideChanges` counter, not `GuideRevision`, which it bumps.
- **Wording:** a row with nothing is **"No guide information"** (the canvas's words for an unmatched channel; the link to the mapping page comes with Settings → Guide in step 5). A gap in the guide — nothing on, something next — reads **"Next 9:00 PM · Title"** in the row and **"Nothing on right now"** in the preview and the OSD.
- **Tests:** 178 matcher tests (the corpus included), 21 for the match job and service, 3 each in the importer and sync suites for the hooks, 12 `DbGuide` tests counting queries through a drift interceptor, 10 `CompositeGuide` tests, and 6 Live TV widget tests that show the imported guide on every row and in the preview **with no network** (the fake short EPG fails any lookup the imported guide should have answered), the minute re-warm, nothing looked up while covered, and the OSD across a programme's end. The gallery's no-guide specimen golden was re-recorded for the wording, and nothing else moved. **1,409 app tests**; the app-launch, keyboard-walk and fault-suite integration tests green under xvfb.
- Left for later: the short EPG's own 5-minute cache doesn't move with the clock (a finished programme can show for up to 5 minutes on a channel only it covers); the player's channel panel still shows no guide line on its rows.

### Settings → Guide (step 5)
Built as in steps 3 and 4 from one written spec: the lead wrote the contract (the domain types and interfaces, stubbed), the page, the picker and their tests; one agent the repository reads, the ranking worker and the importer's part; another the ranking of the picker's guide channels.
- **The page** (`lib/features/guide/presentation/guide_settings.dart`) is the approved sketch in Settings → Playback's layout: Guide data, Keep, Time offset, then the channel list; docs/05 §12 has every rule. The UX calls made here, so they can be overridden:
  - **Counts and the list cover the channels the user can see.** Hidden channels and channels in hidden categories are still matched, but left out of "N of M channels matched" and of the list: a provider of 40,000 channels of which the user kept 600 would otherwise read "612 of 40,000 matched" and bury the dozen that matter. The footer says so. `GuideCoverage` still counts every channel; the page reads the new `ChannelMatchCounts`.
  - **Three lists, not one:** Unmatched (the sketch's), Matched by you (so a mapping can be found and undone) and All, so a wrong *automatic* match can be fixed too, which the sketch's list alone couldn't reach.
  - **The picker keeps the focus in its search field** and ↑/↓ (PageUp/PageDown) move a highlight, as a command palette does, so typing and choosing never trade focus; its rows aren't Tab stops. Up to 50 guide channels, BEST MATCH on an exact normalized name, CURRENT on the one attached now; **Undo my match** on the user's own mapping.
  - **Matching under Unmatched moves the focus to the next channel:** the list is read again and swapped in whole, never cleared first, and its rows aren't keyed by channel, so the focused slot keeps the focus while the matched channel leaves. Working through the unmatched channels is Enter, type, Enter, again. A match shows in its row at once, is saved (`setMapping` / `removeMapping`), then the source is rematched so Live TV and the player follow; the row's optimistic state is dropped only after the list has been read again.
  - **The time offset is a stepper**: one focus stop, ←/→ (or −/+) by 30 minutes from −12 h to +12 h, Enter back to None, a slider to assistive tech. It is saved 1.2 s after the last step, because each save re-imports (decision 4): stepping to +2 h costs one import, not four. Leaving the page saves a step that hadn't settled. A text field would have re-imported per keystroke or needed an Apply button, and the canvas's icon set has no minus for a two-button stepper.
  - **Keep is global** (decision 4): 1, 2, 3, 5, 7, 10 or 14 days ahead, plus yesterday. A change re-imports every source that has a guide (or is importing one), one at a time; a second change stops the first round at its next source. A choice that can't be saved is undone, so no import uses it; days outside 1–14 are refused.
  - **"Updated 2 h ago" is the live guide's time** (`GuideCoverage.updatedAt`, new): after a failed refresh the row still says when the guide in use arrived, and the failure shows under it in amber.
  - **An import that couldn't start says so in a banner** (no guide address, a locked keyring — nothing is recorded, so the row can't show it); one that ran and failed shows in the row.
  - **Live TV's preview links here**, the link promised in step 4: under "No guide information", **Match to a guide channel** opens Settings → Guide for the channel's source with its picker on top (`openGuideMatch`, `GuideMatchRequest`).
- **The seams the page talks to are domain interfaces** (hard rule 6): `GuideImportService` (`EpgImporter`: import, `reimport`, cancel, progress, and `guideOrigin` — where the guide would come from, worked out from the credentials without fetching, so "this playlist names no guide" is a state of the page and not a failed import) and `GuideMatching` (`EpgMatchService.rematch`). `EpgRepository` gained `channelMatches`, `countChannelMatches`, `channelMatch`, `watchChannelMatchCounts` and `matchCandidates`.
- **`reimport` cancels rather than joins** a running import, which read the settings from before the change; two in a row, and only the later one imports (a per-source ticket). The importer reads the days kept from `GuideSettingsController` before its first await, so an import started just after a change keeps the new value. `GuideSettings` is stored under `guide.settings`, tolerant like playback's (an infinite number from `1e999` included).
- **The picker's ranking** (`lib/features/guide/domain/guide_channel_ranking.dart`, pure): a guide channel scores the higher of its name and its id against the channel's `normalizeChannelName` key — 1.0 when equal (for an id, also when equal without spaces), otherwise `0.99 × (0.6 · words + 0.4 · letters)`: words split at spaces and where digits meet letters, each matched to its closest on the other side (numbers only when equal, near words by bigram Dice above 0.5, weighted by length), and Dice over the character pairs of the space-free keys with a run of digits as one symbol. So for "Arena Sports 1": "Arena Sports 1 HD" 1.0 > "Arena Sport 1" 0.905 > "Arena Sports 2" 0.855 > "Arena Sports 10" 0.842. Ties go to the channel's own country, then the label, then the id. A query keeps only guide channels containing it and orders by fit first (equal, starts with, a word starts with, contains). `splitGuideId` / `guideIdKey` / `channelCountryTag` in `epg_matcher.dart` share the matcher's own suffix and country rules (the suffix regex became a scan; the matcher's 178 tests are unchanged). Measured at 50,000 guide channels (debug JIT): prepare 220–227 ms once, a rank 44–51 ms, a query rank 28–32 ms.
- **Ranking never blocks the UI isolate — found by measuring, not by design.** The spec had each keystroke rank in `Isolate.run` above 2,000 guide channels; the data agent timed the synchronous copy of the prepared guide into the isolate at **305–407 ms per keystroke at 50,000** (the copy runs in the VM's native code, so a release build wouldn't help), more than ranking inline. Replaced by `GuideRankingWorker` (`lib/features/guide/data/guide_ranking_worker.dart`): one isolate per (source, live import) that **reads the guide channels itself**, prepares them once, and answers (channel name, query, limit) with at most `limit` candidates; only small messages cross. Measured at 50,000 with a file database: a keystroke costs the UI isolate **0.13–0.18 ms** (22–31 ms end to end), the first call 2.8 ms (521 ms end to end, the worker reading and preparing). It is killed with its entry (a new import, a cleared guide), after 60 s idle, and on the repository's `dispose`; a dead or hung worker fails the query (`TimeoutFailure` after 10 s) and the next call starts a new one. A plain kill, not a guarded job: the worker never begins a transaction and closes its connection before it prepares. At or below 2,000 guide channels it ranks inline. Stale answers are dropped by the picker.
- **Tests:** 24 widget tests for the page and the picker (every state, the three lists, the filter, Enter/↓/Esc in the picker, Undo, a failed save, the Live TV request, Keep, the offset with and without a guide) and 8 wording tests; 45 repository tests (every filter and query, hidden channels and categories, a mapping to an id the guide lacks, the counts watch, `updatedAt`, the worker: equal results, one per import, replaced, idle, dispose, a dead or hung worker, the 2,000 threshold); 42 importer tests (the days from the setting, `reimport`, `guideOrigin` for every kind); 14 controller and 8 settings tests; 39 ranking tests and a benchmark; and a keyboard walk under xvfb (`integration_test/guide_settings_keyboard_test.dart`): Ctrl+, → Guide → Import guide → Keep 3 days → offset +1 h → Enter on an unmatched channel → type → Enter, against the fake panel, 28 s.
- **Left for step 7:** the scheduler must wait for `GuideSettingsController`'s stored value before its first import at launch (it loads asynchronously; an import before then keeps the default 7 days).

### The Guide grid (step 6)

The shell places the focus as the screen opens, often before the guide's coverage is read, so the grid also takes the focus when its rows first show — only when nothing but a route's scope holds it, never from a control.

### The scheduler, the toast, and the phase exit (step 7)
- **When a guide comes in by itself (decision 5):** `GuideScheduler` (`lib/data/sync/guide_scheduler.dart`) imports a source's guide when it has none or the one in use is a day old (`guideRefreshDue`, pure, in `lib/features/guide/domain/guide_refresh.dart`). It looks once the launch's syncs are done (`bootstrap()` calls it after `SyncService.startUp()`), every hour after, and at a source again whenever its sync succeeds (`SyncEngine.onSynced`) — so a first sync brings the guide in behind it. One source at a time, never while that source's sync runs, never beside an import already running for it (Refresh guide in Settings joins the one it started, and tries at once whatever this policy says).
- **It waits for the stored Keep setting** before its first import: `GuideSettingsController.loaded`, a future that completes once the stored choices are read, or couldn't be (the controller now also survives a store that throws).
- **A failed or cancelled import waits six hours** before the scheduler tries again, so a panel that is down isn't asked every hour; one the app was closed during (`interrupted`) is tried at the next check.
- **A source whose import couldn't even start** — no guide address, a locked keyring — recorded nothing, and isn't asked again this session until it syncs: reading a locked keyring prompts for its password, and nobody wants that every hour.
- **Not while a stream is being set up (hard rule 7):** while the playback coordinator is opening or reconnecting a channel of that source, the import waits (up to a minute, then the next check), so the guide's request never competes with a panel's one connection at the moment it matters.
- **The toast** is "Guide updated · 1,284 channels matched", and with two or more sources "Guide updated · Northwind TV · …". N is the **visible** channels matched, as Settings → Guide counts them, not `EpgMatchSummary.matched`, which counts hidden channels too (a provider of 40,000 channels of which the user kept 600 would read "38,120 channels matched"). Only the scheduler's own imports raise it: an import started from Settings → Guide shows its result where it was pressed. A failure raises nothing (decision 5). Background work raises toasts through `AppNotices` (`lib/core/notices/`), which the shell shows; a notice is neither const nor `==`, since tomorrow's identical "Guide updated" must show again rather than be taken for a repeat.
- **Diagnostics:** the import's counts and skipped-row reasons are logged beside the sync's report and stored in `epg_imports.counts_json` as `sync_runs` stores the sync's; the export itself (Copy diagnostics) is Phase 9.
- **The 300 MB import, measured** (`test/data/sync/epg_import_benchmark_test.dart`, `--tags benchmark --run-skipped`; the `large` catalogue synced first, the fake provider in its own process, a file database, debug JIT): **286 MB fetched, parsed, staged, swapped in and matched in 22.0 s** (budget 4 min) — 1,592 guide channels, 611,328 programmes, 41,902 of the 50,000 channels matched; **peak RSS +126 MB** (budget +300 MB); **worst UI-isolate pause 26 ms** (budget 32). The database grows to 469 MB (the programmes and their FTS index). The swap's copy was not the bottleneck: the generation-column fallback isn't needed.
- **The Guide grid, measured and reworked.** `integration_test/guide_scroll_test.dart` scrolls the grid over that same data (50,000 channels, 7 days) in profile mode. The first measurement missed the budget by far (the wheel's median frame 12–13 ms, 36–40 frames over 16 ms in a few seconds of scrolling, → and PageDown to 50 ms), and profile-mode timelines showed where: every cell carried its own focus-ring animation, mouse region and gesture detector; each cache load rebuilt every row; every frame of a horizontal move rebuilt every cell and laid out the text of the programme cut by the view's edge; the grid's query carried every description across isolates; dashed outlines were cut from a path dash by dash. Changed:
  - one mouse region and one tap handler per row, the ring only on the focused cell (drawn over the cells, round the visible part);
  - a row redraws for the cache only when a load for its own channel lands (`GuideWindowCache.revisionOf`);
  - a row builds its cells once for a stretch of the timeline — ±2 h around the view, ±45 min for a row just scrolled in — and slides them with a transform in a layer of their own; the stretch is built again every half hour the view moves, reusing each unchanged cell's widget, so each rebuild lays out a cell or so. The programme the view's edge cuts is drawn on top from the edge (with its ‹), its words laid out once at the whole programme's width and clipped; the sliding layer is clipped past it;
  - rows scrolled in build their cells four a frame, and stretch rebuilds take turns while the view is still inside the old stretch;
  - the grid's window query leaves descriptions out; the detail sheet reads the whole programme (`EpgRepository.programme`);
  - the cache reads the stretch plus an hour either side (step 6 read the view plus an hour);
  - dashes drawn as line segments; each programme's words formatted once.
  **The result, on the real display** (Wayland, profile mode, three runs): **flings 0 frames over 16 ms** (worst 9.4–13.6 ms); the wheel down 1–4 frames over (worst 16.8–17.8 ms); the wheel sideways 0–4 (worst 15.6–22.7 ms); → 4–6 (worst 18.6–25.1 ms); **PageDown 22–28 frames over, worst 59–77 ms**, with UI-isolate pauses of 65–95 ms. So scrolling meets docs/06's "no frame over 16 ms" but for a handful of frames just over it; a page jump, which builds a screen of new rows, does not. The traces also show the semantics phase on this desktop (its accessibility bridge asks for it), so these numbers include what a screen-reader-capable Linux session pays. Under xvfb the same runs wander by 2× (the software rasterizer competes for the CPU), which is why the numbers come from the real display.
- **A bug the end-to-end test found:** Live TV stops playback when it is left, and decided "left" from the router delegate's configuration, which after a push still names the page underneath. Once Live TV had been visited, Watch from the Guide pushed the player, Live TV saw `/guide`, and stopped the stream Watch had just started. Both screens now read `router.state` (the top route); a widget test visits Live TV before watching from the Guide.
- **A step 5 test raced under load** (found by stress-running step 7's tests, 1 in 12 at 6 in parallel): a change of Keep starts its round of re-imports without waiting, the round reads the database, and a test that imported right after could be seen by the round and cancelled. The test now awaits the round (`GuideSettingsController.reimporting`, `@visibleForTesting`); 16 of 16 stressed runs pass.
- **Tests:** 21 new — 5 policy, 10 scheduler (`fakeAsync`), 2 controller, 1 shell toast, 1 repository, 1 cache revision and 1 Guide widget test — the benchmark; and two integration tests: `guide_scroll_test.dart` (the measurement) and `guide_watch_test.dart` — the scheduler imports and toasts → Live TV's first row shows the guide → G → → → Enter → Watch → the player plays channel 1 → Esc stops it and the panel frees the connection (15 s under xvfb, with the samples). **1,616 app tests** (6 skipped) under `TZ=UTC`.

## ADR-012 · 2026-09-27 · Accepted 2026-09-29 (plan approved 2026-09-27; accepted at the phase exit) — Phase 5 movies, series and Home choices
**Decision:** the Phase 5 choices below, organized by step, as docs/plans/phase-5-movies-series-home.md proposed and the user approved on 2026-09-27 — **the recommendation in all seven decisions and the three sketches** (the VOD player with its next-episode card, and Home's first-run hero).

The seven, in short: **1** one `PlaybackCoordinator` for live and VOD, its states carrying a sealed item; `PlayerEngine` gains seek, an open at a start position, the duration and the paused state. **2** details fetched on a page's first open and read from the database after that; movies refreshed in the background after 7 days, series when `last_modified` moved or after 24 h; nothing fetched during sync. **3** Movie details' Resume / Start over is the resume prompt; Continue watching, "Continue S2 · E4" and an episode with progress resume at once. **4** the next-episode card 20 s before the end, a 10 s countdown, Enter now, Esc cancels. **5** Home's rows in docs/05's order, each only when it has something; Continue watching spans every source, the rest follow the browsed source. **6** our own image cache in the app's cache folder (500 MB on disk, 150 MB decoded), extended_image dropped. **7** schema v6: the series' backdrop, genre, cast and director; a movie's video height and audio channels; `watch_history.series_key` and `dismissed`.

Out of this phase: Download and Cast buttons (Phases 8 and 7; left off the details pages, not shown disabled), the Favorites screen and search (Phase 6), Home's offline banner (it points at the Library, Phase 8), catch-up.

### The fake panel serves VOD and artwork (step 1)
- **VOD files** (`tools/fake_provider/lib/vod.dart`): `/movie/…` and `/series/…` serve the item's sample with Range (206, open ends, suffixes, 416 with `bytes */size`; several ranges or another unit are ignored, as HTTP allows), `ETag`, `Last-Modified`, `If-Range` and HEAD. The extension must be the item's own `container_extension`, so a URL built wrong is a 404. Bodies are written on the hijacked connection, like live streams since the soak (ADR-010): a player abandons a connection on every seek, and only the socket's owner sees it go.
- **A request for a file already open takes over the open body's slot** (the old connection is closed), where any other request past `max_connections` is refused. Without it a player's seek on a one-connection panel would be refused: FFmpeg opens the new range before it closes the old one. Whether real panels behave this way is what step 8's play from the user's panel will show.
- **VOD faults:** `drop_after_bytes` counts from the start of the file, not of the body, so the one request that crosses that byte is cut and a player reconnecting past it gets the rest (a drop at a point in the film, once — also what a resumed download needs); `ignore_range`, `throttle_kbps` (kilobits a second) and `http_status` / `slow_start_ms` / `max_connections` as for live. `change_etag`, `wrong_content_length`, `size_mb` and `vod_as_hls` stay with the downloads (Phase 8).
- **Artwork** (`lib/artwork.dart`): logos, posters, stills and backdrops at the sizes real panels link to (256 px, 600 × 900, 500 × 281, 1280 × 720), eight pictures per kind drawn once and served under every item's name with an `ETag` and a week's `max-age`. Every artwork URL in `player_api.php`, `get.php` and `xmltv.php` points at the host the client used, as `server_info` does; the generator still writes its unresolvable host, which the serializers rewrite, so the catalogue itself did not change.
  - **Departure:** PNGs, not the planned JPEGs. The fake provider has no JPEG encoder without a new dependency, and it also runs where ffmpeg isn't installed (the sync benchmarks). A small PNG writer (filter Up, a grain on one pixel in sixteen) gives 158 KB posters, 253 KB backdrops, 44 KB stills and 27 KB logos — near real JPEGs' weight — in 20–140 ms each, once.
- `get_vod_info` has the `video` / `audio` probe blocks and `bitrate` panels store (every 4th movie unprobed: `[]`, `[]`, 0), and movies and series a backdrop (every 5th none).
  - **Departure:** an episode's `duration_secs` stays a realistic runtime rather than its sample's length, and movies' likewise. Probing the samples would need ffprobe in the fake, and the app takes progress from the player's own duration anyway; real panels' metadata doesn't always match their files either.
  - **Departure:** CI's VOD sample (`VOD_SECONDS=120`) moves to step 6, the first step whose tests play VOD; the fake provider's tests use stand-in files.
- **Found:** the server passed any 404 on through a `Cascade`, so the last handler's "Route not found" replaced the reason a stream's 404 gave ("missing sample …", which exists to say what is wrong). Each path prefix now routes to its own handler.
- **Found:** the Guide's keyboard walk and its Watch test failed at some hours of the day: they took a cell's title as its label up to the first ", ", and the fake guide has titles like "Compass Tonight, Ep. 12". The title is now everything before the part with a clock time.
- Fake-provider suite: 140 (114 before).

### Schema v6, the catalogue and history repositories (step 2)
- **One `vod` feature for what the screens share** (`lib/features/vod/{domain,data}`): the grid's query (`TitleQuery`: all, favorites, a category, uncategorized; a filter; Recently added / Name / Rating), the items and details (`MovieItem`, `SeriesItem`, `EpisodeItem`, `MovieDetails`, `SeriesDetails`), `Details<T>` (loading, ready with `refreshing`, failed), and `WatchProgress`. **Departure:** the plan put the repositories in each feature's domain; Movies, Series, Home and the player all need them, so they share one feature and the screens stay in theirs.
- **Schema v6** as decision 7: `series.genre`, `cast_names`, `director`, `backdrop_url` (sync writes them from the list with `COALESCE(new, old)`, so a list that lacks one keeps what `get_series_info` stored); `movie_details.video_height`, `audio_channels` (from the panel's ffprobe blocks, `[]` and zeros read as none); `watch_history.series_key`, `dismissed`. The Xtream parsers keep the series' own `info` and the list's cast, director and backdrop, which they used to drop.
- **Three indexes for the Movies grid, measured:** a window of 120 out of the `large` profile's 30,000 took 27–60 ms whatever the sort (every row joined to its category, favorite and history, then sorted, then the offset skipped). Picking the page's ids on the filtered table first, then joining only those rows, halved it; `movies_added (source_id, added_at, id)`, `movies_name (source_id, name COLLATE NOCASE, id)` and `movies_rating (source_id, rating DESC, name COLLATE NOCASE, id)` let SQLite walk the order instead of sorting: **1.6–19 ms** from the first page to the last, a category 7 ms, favorites 15 ms, the count 18 ms (`--tags benchmark --run-skipped test/features/vod/vod_window_benchmark_test.dart`, file database). "Undated last" and "unrated last" needed no `IS NULL` term: SQLite sorts NULLs last when descending. Series (3,000 at most) have none.
- **The details policy** (decision 2) in `DbMovieRepository.details` and `DbSeriesRepository.details`: the database's copy at once; a first fetch shows loading, then the page or the failure (the row's data stays on screen); a stale copy shows at once, marked `refreshing`, and a failed refresh keeps it silently; an M3U source never fetches; a second page opening while a fetch runs joins it. Proved end to end against the fake panel, whose new per-action counter (`apiCalls`, reported by `/admin/faults`) shows **one `get_vod_info` and one `get_series_info` for two opens**, and **both episode shapes** (`episodesAsMap` on and off) read the same seasons and episodes.
- **`WatchProgress`** (`DbWatchProgress`): a save marks watched at ≥ 95 % of the player's duration and clears a dismissal; a length the player never learned never completes by position; Mark as unwatched forgets the row. Continue watching is worked out again on every change to the history, the catalogue, its details or the favorites: movies between a minute and 95 %, and per series its newest episode that counts (past a minute, or finished) — the one in progress, or the one after it, from its start when it had only a few seconds; a series whose last watched episode was its last has none; dismissing a series marks every episode's row, or an older one would take the newest's place.
- **Found: the short EPG's first answer never arrived** (a Phase 3 bug). `ShortEpgGuide` coalesced requests with `.whenComplete(() => _inFlight.remove(key))`, and `remove` returns the removed future — the very one `whenComplete` made — so it waited for itself forever. The answer still reached the screen late, because the fetch filled the cache before its future hung, and the next minute's refresh read the cache. Fixed with `removeWhere`, and the new repositories, which had copied the pattern, with it; `short_epg_guide_test.dart` fails on the old line (checked) and passes on the new.

### Images (step 3)
- **Our own cache** (decision 6; `lib/data/images/`): `ArtworkCache` keeps files in the platform cache folder (`AppPaths.artwork`, `~/.cache/<app id>/artwork` on Linux) named by two 64-bit FNV-1a hashes of the URL (no new dependency); a file is written as `.part` and renamed once whole; a sweep in an isolate deletes the least recently used (a read moves a file's modified time) down to 90 % of 500 MB, and `.part` files older than ten minutes, at launch and after every 50 MB written. `CachedArtwork` is the `ImageProvider` over it, keyed by URL; `ResizeImage` decodes at the width drawn times the pixel density; Flutter's `ImageCache` is capped at 150 MB (`capDecodedImages`, from `bootstrap()`). extended_image is gone from `pubspec.yaml` (ADR-002 amended), with three packages it brought.
- **Fetching:** six at a time, the newest request first; past 96 waiting, the oldest are dropped, so posters a grid scrolled away from never start (Flutter's `Image` already defers loading during a fling). A 404, a web page served as 200 (the first bytes must be a JPEG, PNG, GIF, WebP or BMP), an answer over 10 MB or 30 s is no picture and isn't asked for again for ten minutes; a cached file that no longer decodes is deleted and fetched again. Failures never quote the URL (`ArtworkUnavailable` carries a reason only; dart:io's errors can name the address).
  - **Departure:** the plan said a dropped request is one "for posters scrolled away"; which widgets still want a picture isn't visible to an `ImageProvider` (Flutter's `ImageCache` listens to every pending load itself), so the queue's length stands in for it. The grid's measurement (step 8) says whether that is enough.
- **Screens ask `artworkFor(context, url, width:)`**, which reads `ArtworkScope` (an inherited widget the app root fills from `artworkImagesProvider`); a widget test without it gets plain network images decoded at size. The six `NetworkImage`s (Live TV's rows and preview, the player's OSD, banner and channel panel, the Guide's rows, Settings → Guide and its picker) moved onto it.
- **`ArtworkImage`** (design component) draws the stand-in — the monogram, the poster's title tile — while a picture loads or when it fails, and cross-fades to the picture in `motion.fast`, the stand-in fading out so a transparent logo never shows the monogram through it. `ChannelLogo`, `PosterCard` and `LandscapeCard` use it.
- **Found:** every Flutter error became a toast, including the *silent* ones Flutter raises for a picture that failed with no widget left waiting for it — which a grid of 30,000 posters would do constantly. `ErrorReporter` now logs silent errors as warnings and toasts only the rest.

  - **Departure:** no typing into the filter from the grid, which the plan offered: F, and D later, are the grid's own keys. The filter is one Shift+Tab away.
- **States:** no source, skeletons, "Getting your movies…" during a sync, "Your provider doesn't offer movies", an empty category (with Show all movies), no favorites yet, no match (with Clear filter), an error with Retry.

- **Found: a list never showed a new star** (Live TV since Phase 3, and the Guide). ## ADR-013 · 2026-09-29 · Accepted 2026-09-29 (plan approved 2026-09-29; accepted at the phase exit) — Phase 6 search, favorites, names and hiding choices
**Decision:** the Phase 6 choices below, organized by step, as docs/plans/phase-6-search-and-polish.md proposed and the user approved on 2026-09-29 ("continue the work") — **the recommendation in all eight decisions and the three sketches**, with the departures recorded where they happen.

The eight, in short: **1** cleaned names stored (`channels.clean_name`, `quality`), filled by sync; a screen shows the rename, else the clean name, else the provider's. **2** what cleanup removes and keeps (below, with one departure). **3** search covers every source, the browsed one first, in the canvas's four groups, up to 5 rows each, prefix matches first. **4** Enter plays a channel or a programme on now, opens the Guide on an upcoming one, and a title's page for a movie or a series. **5** "Remind me" is not in this phase; **the user put it in Phase 9** (2026-09-29). **6** a `favorite_groups` table, per source. **7** the favorites' order and groups carry into Live TV (groups under Favorites in the categories pane) and Home. **8** a channel the user hid is gone everywhere; one in a hidden category stays only where it is a favorite; Settings → Categories gets a Hidden channels tab.

### Channel name cleanup (step 1)
- **`cleanChannelName`** (`lib/features/live_tv/domain/channel_names.dart`, pure) returns the name to show and a `ChannelQuality` (SD, HD, FHD, 4K). Its tag tables and scanners moved out of the guide's matcher into `channel_name_tags.dart`, which both use: the matcher's 144-line corpus did not move. The scanners now read either case (the matcher reads a lower-cased name, the cleaner the provider's capitals), and a leading tag may be a quality word (`4K |`, `(4K)`, `[HEVC]`), which the matcher then drops as it always did.
- **The rules:** entities decoded however often escaped; odd whitespace, control characters and U+FFFD read as spaces, runs collapsed; leading country and language tags dropped where a separator or brackets mark them, as the matcher reads them (`TV 5 Monde`, `ABC News` keep their first word); resolution tags at the end — plain, superscript (`ᴴᴰ`), bracketed (`(HD)`), two-word (`Full HD`) or as lines (`1080p` → FHD, `720p` → HD, `576i` → SD, `2160p` → 4K) — become the badge, the highest winning; `+1`, numbers, the provider's capitals and punctuation that is the name's (`Canal+`, `Nick Jr.`, `E!`) are kept; a name with nothing left but tags stays as the provider wrote it, with no badge. Cleaning a cleaned name changes nothing (a fuzz test checks 5,000 random names).
- **Departure from decision 2: technical tags stay in the name.** The plan removed codecs (`HEVC`, `H.265`), frame rates (`50fps`) and `Backup` with no badge. Real panels list one channel several times — `ESPN`, `ESPN HEVC`, `ESPN (Backup)` — and with those words gone the rows would read the same, with nothing to choose between them. So only what becomes the badge goes: `UK: Sky Sports F1 FHD HEVC` shows as **Sky Sports F1 HEVC** with FHD; `History (Backup)` stays as it is; a leading `[HEVC]` moves after the name. The matcher still drops them all. (Decided under "decide UX"; easy to reverse in `technicalWords`.)
- **Schema v7:** `channels.clean_name` and `quality` (provider-owned: in the channels DAO's `DoUpdate` list, so a re-sync rewrites them with the name; `display_name` stays the user's); `favorite_groups` (source, name, order, collapsed; removing the source removes them); `favorites.group_id` in place of the never-written `group_name` (a deleted group leaves its channels favorites, in no group). `favorites` is copied to change its column (`TableMigration`).
- **Search indexes the name shown:** `channels_fts` is now `(clean_name, display_name)`, rebuilt in the upgrade, so "uk" or "hd" never matches a channel by its tags. Before the fill reaches a row (below), only its rename is searchable.
- **Sync** cleans every channel in its isolate (`withCleanName`, Xtream and M3U alike); 50,000 names clean in about 175 ms (debug JIT).
- **The fill for catalogues synced before v7** (`ChannelNameFill`, `runChannelNameWork`): after launch, before the launch syncs, one query asks whether any channel lacks a cleaned name; if so, a guarded job names them 5,000 at a time in row id order, each batch one transaction, and never overwrites a row a sync wrote meanwhile (`WHERE name = ? AND clean_name IS NULL`). A stop between batches leaves whole batches only, and the next launch carries on. Rows show the provider's name until it reaches them.
- **Repositories:** `ChannelItem` gains `quality`; its `name`, the name sort and the text filter use the rename, else the cleaned name, else the provider's name (`COALESCE(display_name, clean_name, name)`), in Live TV, the Guide, Home and the player's panel, which all read `DbChannelRepository`, and in Settings → Guide.
- **Tests:** the corpus (`test_fixtures/channel_names/names.tsv`, 111 names: every docs/05 pattern, the plan's additions, and names that must keep their words), odd names (empty, blank, tags only, entities escaped twice, U+FFFD, lone surrogates, emoji, Arabic, Cyrillic, Greek, 500 characters, unbalanced brackets) and the fuzz; the migration from a populated v6 database and the index after it; the DAO (a re-sync rewrites the name and badge and keeps the rename); both kinds of sync; the fill (batches, names already there, odd names, a stop between batches three times over, the service's single run and its stop); the repository (the name order, the sort ignoring tags, the filter on the name shown).
- **Measured:** the fill names 50,000 channels in **1.2 s** (10 batches of about 120 ms, each holding the database while it commits; `--tags benchmark --run-skipped test/data/sync/channel_name_work_test.dart`, file database, debug JIT).

### Clean names and badges on screen (step 2)

### Search: the query (step 3)
- **`SearchRepository`** (`lib/features/search/domain/search.dart`; `DbSearchRepository` in `data/`, `searchRepositoryProvider`): `search(text, now:, preferredSourceId:)` gives the four groups — `ChannelHit`, `ProgrammeHit`, `MovieHit`, `SeriesHit`, each with its source's name and its category's — up to 5 each with `hasMore`, the number of hidden channels that match (counted only when no visible one does), and how many sources there are; and the recent searches (the last 8, newest first, once each whatever the case, in the settings table under `search.recent`; anything stored that isn't a list of text reads as none).
- **The words** (`searchWords`, pure): runs of letters, marks and digits in any script, at most 8 of 64 code points; each becomes a quoted prefix term, all required. Quotes, `*`, `-`, parentheses, `NEAR(`, emoji and lone surrogates are only separators, so no text reaches FTS as syntax (a fuzz test sends 300 mixes).
- **The order, as decision 3:** in every group the browsed source first. Channels: favorites, then names that start with the text, then a word that does, then the index's rank, then the name. Movies and series the same without the favorites step. Programmes: by start, which puts what is on now first.
  - **Decided:** among channels, favorites come before a closer name: the plan lists both rules without saying which wins, and a favorite is the more specific wish.
  - Two names equally close go by the index's rank (BM25), which puts the shorter name first ("Arena Starred" before "Arena of Kings" for "arena").
- **Visible** is decision 8's rule in SQL, the same as Live TV's: a channel hidden itself never shows; one in a hidden category only as a favorite; movies and series follow their category the same way. A programme shows only on a visible channel, and an HD/SD pair on one guide id is one hit, on the favorite of the two, else the one the provider listed first.
- **Measured, and changed:** the first version sorted every programme that matched, and a short word matches much of a guide — "t" 276,712 of 611,328 programmes, "the" 203,379. **One to three characters took 0.7–5.2 s**, all in the programme query (channels 8 ms, movies 22 ms at worst). The database isolate would have been blocked that long for every other query. Now:
  - **The guide's swap inserts programmes by start time** (`ORDER BY start_utc, epg_channel_id`; about 0.7 s more for 600,000 rows in a 22 s import), so a source's row ids follow its schedule — ids only grow (`AUTOINCREMENT`).
  - **Each source's programmes are read in row id order** from the first programme on now (the lowest id of each matched guide channel's latest start; about 6 ms, remembered for five minutes — an older answer is still a valid lower bound, only a little further back) **and the read stops at 6.** Programmes on now all started before anything upcoming, so row id order is on-now-first, then by start.
  - **One-letter words don't reach the programme index:** they only narrow what the longer words found (a word in the title or subtitle starting with that letter), and a text with no longer word finds no programme. Channels, movies and series answer from the first letter.
  - **The result** (`--tags benchmark --run-skipped test/features/search/search_benchmark_test.dart`: the `large` catalogue synced from the fake panel in its own process, 611,328 programmes over 8 days, a file database, 55 texts of 1–20 characters, three rounds): **median 6.6 ms, p95 24 ms, worst 31 ms** ("t"), against the proposed budget of **50 ms per query**; the UI isolate's longest gap 4 ms. By length: one character 26–31 ms, two 15–24, three 12–21, four and more under 14.
  - **Transition:** a guide imported before this build keeps the provider's order until its next import (at most a day, the scheduler's policy). Until then, programme hits are still all not finished and visible, but not necessarily the soonest.
- **Tests:** 22 — every group, each ordering rule, the hiding rules, two sources, the HD/SD pair and its favorite, title and subtitle but not description, one-letter words, a programme 20 hours long still on now, text with no word, the fuzz, LIKE characters, recent searches; the swap's start order; the words (scripts, syntax as separators, the limits, a cut never splitting a surrogate pair). **1,985 app tests** under `TZ=UTC`.

- **Windows: a file a job had open stayed open after the job was stopped.** A killed isolate's files close only when they are collected, so Windows refused to delete the tests' folders (`M3U a big file is only read to its first entries`, `removing a source mid-sync stops the sync first`) — and would have refused to move or delete a user's playlist for a while after a check or a cancelled sync. Now:
  - `parseM3u` ends early and cleanly on `StopReading` (thrown or returned by `onEntry`) or when its `stop` future completes: the input is cancelled, the file closed, before the summary of what was read comes back.
  - **The playlist check** reads with `readM3uInBackground(stopAfter:)` and waits for the reader to stop itself; the kill is only the timeout's last resort.
  - **A guarded job asked to stop** runs what its task registered with `JobCancellation.beforeStop` before it answers that it can be killed; the M3U sync registers its read there. A close that fails or hangs still ends in the kill (the grace period).
  - **Tests** read `/proc/self/fd` on Linux, where every isolate's files show: after a check, and after a source removed mid-sync, the playlist is not open. Both fail on the old code.
- **The database keeps a write-ahead log** (`configureAppDatabase`: `journal_mode = WAL`, `synchronous = NORMAL`, the log cut back to 64 MB after a checkpoint). With the rollback journal every commit waited for several disk syncs; the Windows CI's 30 s timeouts were all tests of many small commits on a file database (a sync in batches of 50, twice; an import cancelled and run again), and Windows' disk syncs are slow. **Measured here:** the cancel test's body 4 s → 1.5 s; the `large` first sync 6.5 → 5.8 s, re-sync 3.9 s either way, the 27 MB playlist 16.2 → 12.0 s; the whole suite 85 → 79 s. **The trade:** a crash of the app loses nothing committed; a power cut or a crash of the system may lose the last commits (a favorite, a watch position), never the file's consistency. The hard-rule-3 test now keeps its database the same way and scans the log file too. Whether it clears the Windows timeouts shows on the next CI run.

## ADR-014 · 2026-09-29 · Proposed (plan approved 2026-09-29; accepted at the phase exit) — Phase 7 casting choices
**Decision:** the Phase 7 choices below, organized by step, as docs/plans/phase-7-casting.md proposed and the user approved on 2026-09-29 ("do the recommended") — **the recommendation in all eight decisions and the five sketches**, with the departures recorded where they happen.

The eight, in short: **1** movies and episodes cast in this phase too (a file the TV plays as it is goes direct with Range; anything else through the relay as one continuous stream, a seek restarting it). **2** while casting, everything played goes to the TV; the Live TV preview opens no stream of its own; Cast while watching moves what plays. **3** FFmpeg and ffprobe read the provider through a loopback proxy inside the relay (no credentials on a command line, the URL rebuilt per reconnect, the connection visible to the app). **4** the plan's facts from the laptop's player, then a probe remembered this run, then ffprobe (8 s). **5** the relay in its own long-lived isolate. **6** bonsoir and multicast_dns side by side, merged by device id, plus Add by IP address. **7** the desktop portal's Inhibit (logind as the fallback) over the `dbus` package on Linux, `SetThreadExecutionState` on Windows. **8** `tools/fake_receiver`, which fetches and checks what it is told to play.

### Discovery, known devices, FFmpeg in the build (step 1, 2026-09-29)

  - `MulticastDnsCastBrowser`: a round every 8 s — PTR `_googlecast._tcp.local` for 3 s, each answer's TXT, SRV and A taken as they come (a Cast device sends them with the PTR, so they are in the client's cache) — and a device dropped once it misses **two rounds in a row**. Each connects, asks GET_STATUS and joins the same app by its session id (or transport id), CONNECTs and asks the media status; the TV plays on meanwhile. The app gone → the session ends as above; nothing within 30 s → `lost`.

- **Learning** (docs/04), when the refusal comes **within 10 s of a direct LOAD or 15 s of a relayed one**, in this order: a direct play → the relay for the source from then on; **a picture sent taller than 1080p** (the plan's output, so a re-encode kept at 2160p is caught too) → 1080p; a copied picture codec other than H.264 → refused; an interlaced picture copied → deinterlaced; **a copied sound other than AAC** (MP3, Dolby passed through) → converted. Saved to the device (`setLearned`), planned again — a plan equal to the refused one fails ("can't play") —, a `CastPlanChanged` notice, the old relay session stopped and the new plan carried out. At most 4 lessons a play. **A refusal later than that:** a live stream that played is loaded again; a file fails with Try again.
- **Following the relay:** `CastRelayFetched` (and PLAYING) cancel the **10 s "couldn't reach this computer"** rule, which otherwise fails the cast (the TV is told to stop). `CastRelayOpened`: remembered in the facts lookup; **planned again only when the picture's codec or height or the sound's codecs differ** (FFmpeg reports fewer fields than ffprobe, and a field it leaves out mustn't change the plan) **and the new plan does something else** (delivery, picture or sound, a bit rate apart). `CastRelayStreamsChanged` (a codec switch): forgotten, probed again on a fresh connection after the old session let go of its own, planned again, a new LOAD. `CastRelayFailed`: a re-encode tries the next encoder (`detectAgain`, then `after`; at most 4), anything else fails with docs/03's words (`classifyStreamFailure` on the provider's status and first bytes; unreachable → network; unresolved → unavailable; the relay's own connections → the connection limit; FFmpeg and the budget → the relay).
- **Automatic LOADs are budgeted:** a live stream the TV dropped, a codec switch, a file cut short — 3 within 2 minutes, then the cast fails. The relay's own restart budget (5 in 2 minutes) counts its renews too.
- **One attempt at a time:** every new attempt at what plays (a re-LOAD, a new plan, a seek, a codec switch, the next encoder) **bumps the cast's generation**; work of an older one stops counting after each wait, and a relay session started for it is stopped at once. (Found while writing the codec switch test: a TV error and the switch arriving together could each start a session and leave one running.)
- **Files** (decision 1): the place is the TV's time plus where the relay started, moved on by a clock between the TV's reports; a seek of a direct file is the TV's own, of a relayed one a `renew(startAt:)` and a new LOAD, "Preparing…" meanwhile; the place saved every 10 s while it plays, on pause, after a seek, on Stop casting, on a failure, and at the end; Play here continues it on the laptop from the TV's place.
- **Sleep** (decision 7): held while a cast prepares or plays, let go otherwise. `SleepInhibitor` (`lib/core/platform/`), `DbusSleepInhibitor` (`lib/data/platform/`): **the desktop portal's `Inhibit` with suspend and idle (flags 4 | 8) and the reason "Casting to Living Room TV"**, let go by closing its request; **logind's `Inhibit("sleep:idle", "block")`** when there is no portal, let go by closing its descriptor; false and a log line when neither answers. **Checked on this laptop (GNOME):** `gnome-session-inhibit --list` shows "Casting to Living Room TV (test) (suspend, idle)" while held, and nothing after. ## ADR-015 · 2026-10-04 · Proposed (plan approved 2026-10-04; accepted at the phase exit) — Phase 8 downloads and library choices
**Decision:** the Phase 8 choices below, organized by step, as docs/plans/phase-8-downloads-and-library.md proposed and the user approved on 2026-10-04 ("all approved based on ur recommendations") — **the recommendation in all twelve decisions and the eight sketches**, with the departures recorded where they happen.

The twelve, in short: **1** Phase 8 starts while Phase 7's TV sitting waits. **2** downloads move their bytes in an isolate of their own (dart:io), the queue's rules stay in the app's isolate, and the URL is asked for on every connection. **3** downloads yield through `SourceConnections`: the newest on a source lets go at once when the player or a cast needs room, and they come back 10 s after the source is free. **4** an item that answers with HLS is saved by FFmpeg through a loopback proxy, with no resume. **5** a download keeps a copy of its details (`library_items.details_json`) and `poster.jpg`. **6** a two-pass scanner as a guarded job: walk, stat, quick hash and parse first; ffprobe after; thumbnails when first shown. **7** watched folders, rescanned 3 s after the last change, with "Updates when rescanned" as the fallback. **8** every Play of a downloaded title uses the file (the resolver looks for it first); your own files are a `PlayableLibraryItem`; no reconnects on disk. **9** Enter opens a page for movies and shows, plays a video. **10** Delete goes to the trash through our own freedesktop trash spec on Linux, `SHFileOperationW` on Windows, else a second confirmation. **11** offline from NetworkManager over D-Bus (Windows' Network List Manager), the app's own failures as the fallback. **12** library files cast directly when the TV takes them; otherwise the continuous relay at once and an MP4 made beside it so later seeks are native; text subtitles as WebVTT.

### Schema v9, the domain, the download folder (step 1, 2026-10-04)
- **Schema v9** (`lib/data/db/library_tables.dart`, `library.drift`): docs/09's `library_folders`, `library_items`, `downloads` and `library_fts` (title, show title; external content kept by triggers like the others, recreated on every upgrade). **Departures from docs/09's table**, each small:

  - `library_folders.label` (the canvas names folders: "Movies HDD", "USB drive");

### The download engine (step 3, 2026-10-04)
- **Built:** `lib/core/downloads/` — `download_paths.dart` (docs/09's layout; `safeName`: Windows' refused characters and control characters dropped, no trailing dots or spaces, reserved names get `_` after the stem (`LPT9_.mkv`), 120 characters a part by letters not bytes, `Untitled` for nothing; `freeName` adds ` (2)`; on Windows title parts shrink until the path fits 240), `download_runner.dart` (the runner's interface and its sendable messages); `lib/core/platform/shared_sleep.dart` (one system hold for the cast and the downloads); `lib/data/downloads/` — `HttpDownload`, `HlsDownload`, `download_isolate.dart`, `IsolateDownloadRunner`, `DbDownloadStore`, `FileDownloadFinisher`; `lib/data/library/quick_hash.dart` (size + FNV-1a 64 over the first and last 64 KB); `lib/data/platform/disk_space.dart` (`statvfs` through FFI; `GetDiskFreeSpaceExW`, untried); `lib/features/downloads/` — `DownloadQueue` (domain), `download_ports.dart`, `CatalogueDownloadTitles`, the providers. `SourceConnections.giveWay` and `changes`. `bootstrap()` starts the queue after launch and shuts it down in the quit tasks.
- **Decision 3 as built:** a holder that gives way registers with `SourceConnections.giveWay`; `room()` asks it to let go before waiting, so the player's wait ends as the download's connection closes (milliseconds), not after 5 s. The queue stops the newest run on that source (or, while it is still asking for its URL, drops it at once) and marks it `waitingForConnection`. When the other holders' count at a source falls to 0 the source stays quiet for 10 s; a zap within that keeps the downloads waiting. "Downloads paused while you watch" is told once a viewing. A download queued while the player has the source waits for the connection too.
- **docs/09's rules, as built:** resume from the `.part`'s size with `Range` + `If-Range` (ETag, else Last-Modified); 206 appends; 200 empties the `.part`; a 206 from the wrong place or a 416 that doesn't match starts over without Range (twice at most); a 416 ends it when the size matches **the size the 416 names** (a provider whose Content-Length lies, `wrong_content_length`, then still finishes, and verification judges the file). The errors: network and 5xx → 2, 4, 8, 15, 30, 60 s, then every 60 s, failed after 30 min without progress (progress resets the count); 401/403 → every download of that source paused with the account problem until resumed; a 403 whose body speaks of connections is the connection limit, as docs/03 classes it; 404/410 and a title gone from the catalogue → failed; 429 and the limit → wait 60 s; a write error → failed. Disk space: the rest of the file + 1 GB before starting and every 256 MB; short of it everything pauses with a banner until Resume all. Speed limit by pausing the read. At launch, what was running goes back in the queue from its `.part`'s size (or paused with resuming off); at quit, runs stop and flush and stay as they were.
- **Departures:**
  - **The file is forced to disk (`fsync`) every 64 MB, not 8** (and on pause and at the end): Dart's `flush()` is an `fsync`, and at 8 MB the syncs took the speed from about 1 GB/s to 580 MB/s on this laptop's SSD. A crash of the app loses nothing already written (the page cache keeps it), and the `.part`'s size is what a launch trusts; only a power cut can lose the last 64 MB, which the next launch fetches again. The database row is still written every 8 MB of progress.
  - **Cancel deletes the `.part` and takes the download off the list** (the canvas has no "canceled" section, and the title's Download button is back); `DownloadTaskState.canceled` stays for a row an older build may hold.
  - **ffprobe that can't start or times out doesn't make a download damaged:** the size check stands alone and the item has no length until the scanner probes it. Only a file ffprobe opens and can't read, or reads no length in, is damaged.
  - **No idle timeout wrapped round the body:** a check every second (or a quarter of the idle time) closes a connection quiet for 30 s; the wrapper cost a fifth of the speed at 1 GB/s.
- **The finisher:** the size against the provider's, then ffprobe on the `.part`, then the rename (a name taken meanwhile gets a number), then `poster.jpg` from the app's picture cache (a show's poster in the show's folder), the details copy (decision 5: a movie's row and `movie_details`; an episode's and its series'), and the library item with its provider link, quick hash and length. A crash between the rename and the database finishes from the final file at the next try. A damaged file's `.part` is deleted: **no file under a final name was ever unverified.**
- **HLS (decision 4):** a playlist answer (the content type, or a body starting with `#EXTM3U`) hands the download to FFmpeg in the same isolate, reading through a `RelayProxy` there (no credentials in its arguments, each segment's connection counted); Matroska out; no resume. The fake panel's `vod_as_hls` saves end to end and ffprobe reads 9.0 s of a 9 s clip.
- **Found on the way:** awaiting a `StreamSubscription.cancel()` waits on a root-zone future, which leaves a test's fake time (the first queue tests hung on it); `SourceConnections.room()` and the queue no longer await their cancels. The finisher's ffprobe types bring Flutter in (`stream_facts.dart`), so the SIGKILL victim runs the queue with a stand-in finisher.
- **Measured** (`flutter test --tags benchmark --run-skipped test/tools/download_measure_test.dart`, the fake panel in its own process, both clients writing to the same SSD): **at network rates the app is 99.6 % of curl** (1 Gbps: 118 vs 119 MB/s; 100 Mbps: 12 vs 12 MB/s). **Over loopback, unthrottled, it is 35 % of curl** (675 MB/s vs 1.9 GB/s): a plain `HttpClient` writing to a file reaches about 0.8–1 GB/s here, so loopback measures Dart's HTTP stack, not the downloader. **For your review: docs/06's "≥ 90 % of curl" is now checked at network rates, with loopback reported.** Memory over a 4 GiB download at 1 Gbps: **+20 MB and +31 MB** at the peak in two runs (budget 30), the same in every quarter of the file — a working set, not growth; over loopback +22 MB steady after a first peak of +37–61 MB.
- **Exit criterion, as tests** (`download_kill_test.dart`, a `dart run` victim killed with SIGKILL): killed at 12 MB of a 40 MB download, nothing exists under the final name, the next launch resumes from the `.part` (it opened at the `.part`'s size) and every byte of the file is right; a playlist's FFmpeg ended with its app (its input was the dead app's proxy: gone by the first look) and the next launch's sweep left no PID file.

### Names and the scanner (step 4, 2026-10-04)
- **Built:** `lib/data/library/` — `name_parser.dart` (`parseVideoName`), `library_scan.dart` (the guarded scan job), `library_probe.dart` (ffprobe for a library file), `library_thumbnails.dart`, `system_trash.dart`; `lib/core/library/library_media.dart` (`LibraryMedia`: length, picture, sound and subtitle tracks, the title tag, the quality line "1080p · H.264 · AC-3 5.1"); `lib/features/library/data/` — `LibraryScans` (one scan at a time, at launch, on Rescan and a folder added, and on a watched folder's changes), `DbLibraryRepository`, the providers. `bootstrap()` starts the scans after the download queue; thumbnails go in `<cache>/library/thumbnails`.
- **NameParser** (pure, never throws): `SxxEyy` with `E05`, `-E05` or `-05` for a second episode; `2x04`; a numbered file in a season folder (`Season 2`, `S02`, `Series`, `Saison`, `Staffel`, `Temporada`; `Specials` is season 0) with the show from the folder above; `[Group] Show - 04` as season 1; `Title (Year)`, `Title [Year]`, `Title.Year…`; else unsorted. The year is the last one before the release tags (`Stars 2049 (2017)`, `1917 (2019)`, `2001 A Harbour Odyssey (1968)`). **Two rules the corpus led to:** a bare year counts only in parentheses or brackets, in a dotted scene name, or followed by release tags — "Birthday at the lake 2021" stays a home video; and dots and underscores part words only in names without spaces — "Mr. Robinson's Garden" keeps its dot. A tag right after an episode's code is a tag (`S01E01.720p…` has no title). The corpus is `test_fixtures/library/names.json`: docs/09's seven and 43 more, all fictional.
- **The scan (decision 6), as built:** pass 1 walks with docs/09's skips (hidden, `.part`, under the minimum, `sample`/`trailer`/`featurette` words, and folders named Sample(s), Trailers, Featurettes, Extras, Behind the Scenes), stats every video, quick-hashes only new or changed ones, parses names, finds subtitles (`Movie.en.srt`, `Movie.eng.forced.srt`, `Movie.English.srt`; SDH/CC words ignored) and pictures (`<name>-poster.jpg`, `<name>.jpg`, `poster`/`folder`/`cover`, and a season folder's videos take the show folder's), and writes in batches (500) as one transaction each. **A row whose file is gone waits until every folder is walked:** a new file with its hash, in that folder or another, is the same file moved (its id, history, favorites, edits and hiding go with it); what nobody claims is removed at the end (its history stays, keyed by the hash). A changed file is hashed and probed again; the user's edits are never overwritten. A folder that can't be read: not available, its items "not connected" from now, removed after 30 days; back in time, as before. Pass 2 probes what has no `probe_json`, 4 at a time, 20 s each; an unreadable file is marked so and not asked again until it changes; an unsorted video without the user's edit takes its file's title tag.
